1. Hot Key 与 BigKey 的本质区别？为什么 Cluster 不能自动解决单个 Hot Key？

Hot Key 是访问流量集中，BigKey 是单个 Value 或集合规模过大。同一个 Redis Key 会映射到固定 slot，所以增加 Cluster 节点只能分散不同 Key，不能自动把单 Key 流量拆开。

2. 为什么“Hot Key 加分布式锁”通常答偏？

锁主要解决缓存失效时多个线程同时重建导致的击穿。如果热点 Key 一直存在且持续命中 Redis，锁并不会减少对该 Key 的读取流量。

3. BigKey 为什么危险？为什么删除时考虑 UNLINK？

大 Value 会增加网络传输、命令处理、内存回收和 Cluster 迁移成本。UNLINK 将实际内存回收异步化，可减少删除大对象对主执行路径的阻塞。

4. Tool Calling 与 MCP 的职责边界？

模型通过 Tool Calling 决定工具和参数；Host 负责调度；MCP Client/Server 提供标准化工具连接和执行通道。权限仍须服务端校验。

5. AI/RAG 性能优化为什么不是先加缓存？

应先把 Embedding、Retrieval、Rerank、Context、LLM TTFT/Generation、Tool Call 分段观测，确认真正瓶颈后再优化。

后端 #92｜Redis 为什么要序列化？常见方式怎么选？

出处：《后端高频面试题大集合》Redis 序列化相关题。

白话：Java 内存里的 User 对象不能原样跨进程保存到 Redis。序列化就是把对象变成可存储/传输的字节表示；反序列化负责恢复。

Java Object → Serializer → bytes/JSON → Redis → Deserializer → Java Object

String 简单透明；JSON 可读、跨语言但体积较大且要处理类型/字段演进；JDK Serialization Java 绑定强、可读性和跨语言性差；Protobuf 等二进制协议通常更紧凑，但需要 schema 管理。

Spring 项目：字符串 Key 通常使用 StringRedisSerializer；对象 Value 可统一采用团队约定的 JSON serializer，并明确日期、泛型、类型信息和版本兼容策略。

AI补充/纠错：Redis 本质存储字节序列，并不要求 Java 对象必须使用某一种固定序列化方式。不要把 Spring Data Redis 默认配置等同于 Redis 协议要求。

常见坑：同一 Key 不同服务使用不同 serializer；类改名后旧缓存无法反序列化；缓存中保存不安全的多态类型信息。

追问：为什么不推荐随意用 JDK Serialization？如何处理 DTO 字段升级？Redis Hash 与整对象 JSON 怎么选？回答应围绕跨语言、体积、兼容性和局部更新成本。

30秒口述：Redis 存的是字节数据，所以 Java 对象要通过约定的序列化协议转换。项目里 Key 常用字符串，Value 常用 JSON 或更紧凑的二进制协议；选择时看跨语言、可读性、体积和版本兼容，并保证所有服务使用一致协议。

一句话：序列化就是约定“对象怎样变字节、字节怎样变回对象”。

后端 #93｜Redis RDB 与 AOF

出处：《后端高频面试题大集合》Redis 持久化相关题。

白话：Redis 主要在内存里工作，进程或机器重启后要恢复数据，就需要把可恢复的信息落盘。RDB 像定期拍照片，AOF 像持续记账。

RDB: 内存状态 → 某时点快照 → RDB 文件
AOF: 写命令 → 追加日志 → 按策略刷盘 → 重启恢复

RDB 文件紧凑、适合备份和快速加载，但两次快照之间可能丢数据；AOF 通常可把数据丢失窗口压得更小，但写盘、日志管理和恢复路径更复杂。

为什么：这是典型 RPO/RTO 权衡：允许丢多少数据、希望多久恢复，以及能接受多少运行期开销。

AI补充/纠错：现代 Redis 的 AOF 已有重写和多文件等实现演进，不能只背“一个无限增长的大日志从头重放”。具体行为应以所用 Redis 版本为准。

追问：AOF everysec 会不会完全不丢数据？RDB fork 有什么成本？AOF rewrite 是什么？回答要强调刷盘策略、Copy-on-Write 与日志压缩/重写。

30秒口述：RDB 是周期快照，恢复快、文件紧凑，但快照间可能丢数据；AOF 记录写操作，通常能提供更小的数据丢失窗口，但运行和恢复成本更高。生产选型要结合 RPO、RTO 和 Redis 版本能力。

一句话：RDB 是拍照，AOF 是记账。

后端 #94｜持久化、复制、Failover、Backup 为什么不是一回事

出处：承接《后端高频面试题大集合》Redis 持久化/高可用相关题；本题结构化对比属于“AI补充/纠错”。

能力解决的问题
RDB/AOF进程重启后如何恢复数据
Primary/Replica是否有在线副本
Sentinel/Cluster FailoverPrimary 故障后谁接管
Backup误删、逻辑损坏或灾难后如何回到历史状态

例如管理员误执行删除命令，复制可能迅速把删除同步到 Replica；Failover 只能换节点，不能把被删的数据变回来。这时历史 Backup 才可能有价值。

AI补充/纠错：“开启 AOF 就等于高可用”是错误理解。持久化解决恢复介质，高可用还涉及冗余、故障检测和自动切换。

追问：Replica 能否替代 Backup？Sentinel 和 Cluster 的目标有什么差异？AOF 文件损坏怎么办？

30秒口述：持久化、复制、故障切换和备份解决的是不同故障模型。RDB/AOF 负责重启恢复，Replica 提供在线冗余，Sentinel/Cluster 做故障切换，Backup 用于误删或灾难后的历史恢复，不能互相简单替代。

一句话：落盘不等于副本，副本不等于备份。

Agent 1.1.11｜结构化输出为什么比 Prompt 要求 JSON 更可靠？

出处：《AI应用开发面试题 / Agent / RAG》结构化输出相关内容。原资料如以 Python/Pydantic 展示，此处转换为 Java/Spring 视角。

白话：Prompt 里写“请返回 JSON”只是自然语言要求，模型仍可能加解释、漏字段或类型错误。结构化输出把结果定义成明确契约，让宿主按 schema 解析并验证。

User → Prompt → LLM → Structured Response → Java DTO/record → Validation → Service

Java 中可用 record/DTO 表达字段，再配合框架提供的结构化输出能力和 Bean Validation 做业务校验。例如金额即使是合法 number，也仍要检查是否大于 0；Schema 正确不代表业务正确。

AI补充/纠错：核心不是 Pydantic 这个 Python 库，而是“类型化输出契约 + 解析 + 校验”。模型 API/框架是否能严格约束 schema，要看具体实现。

追问：Schema validation 与业务 validation 区别？模型漏字段怎么办？结构化输出能防 Prompt Injection 吗？最后一题答案是否定的，它不是安全边界。

30秒口述：只在 Prompt 要求 JSON 属于软约束，模型仍可能产生格式漂移。结构化输出通过 schema 定义字段和类型，再映射到 Java DTO 并做校验，能让下游代码更稳定；但权限和业务规则仍必须由服务端验证。

一句话：Prompt 是“请这样写”，Schema 是“按这个接口交付”。

AI基础 #47｜大模型流式推理

出处：《AI大模型面试题-基础篇》流式输出/推理相关题；Spring AI 与 SSE 部分为“AI补充/纠错”。

白话：模型生成答案是一段一段 Token 往后生成。非流式通常等完整答案生成后一次返回；流式则生成一部分就推一部分，所以用户更早看到内容。

Client → Spring Boot → LLM
                  ← chunk/token
       ← SSE/stream chunk
                  ← next chunk
       ← SSE/stream chunk

关键指标是 TTFT（Time To First Token）。Streaming 通常明显改善用户感知延迟，但不保证完整答案生成总时间变短。

Spring AI：可使用流式 Chat API 获得 Reactor Flux，再通过 Spring WebFlux/SSE 向前端持续推送。生产上还要处理客户端断连、取消传播、网关 buffering、超时和背压。

SSE vs WebSocket：SSE 更适合服务端持续向浏览器单向推送文本；WebSocket 是双向长连接，适合双方都需频繁主动发送消息的场景。普通 LLM 文本流常用 SSE 已足够。

追问：Streaming 会降低 Token 费用吗？不会。为什么 Nginx 后面看起来还是一次返回？可能是代理 buffering。用户关闭页面后模型还在生成怎么办？要把取消信号向上游传播并释放连接。

30秒口述：大模型流式输出是在生成 Token 的同时逐块返回结果，主要降低 TTFT 和用户感知等待时间。Java/Spring AI 可以结合 Reactor Flux 和 SSE 实现；生产上要特别处理网关缓冲、断连、取消和超时。它不等于模型总推理时间一定下降。

一句话：Streaming 让你更早看到，不等于模型更早算完。
