1. 事务传播属性和隔离级别分别解决什么问题？

答完后展开

传播属性解决调用链已有事务时当前方法如何参与；隔离级别解决并发事务之间的数据可见性。

面试口述：传播看事务边界怎么传，隔离看并发事务能看到什么。

2. 为什么同类 this.xxx() 调用经常让 @Transactional 失效？

答完后展开

Proxy 模式下 self-invocation 没经过 Spring 代理，事务拦截器没有机会增强。

3. REQUIRED、REQUIRES_NEW、NESTED 最大区别？

答完后展开

REQUIRED 加入外层；REQUIRES_NEW 挂起外层并开独立物理事务；NESTED 常依赖 Savepoint 做局部回滚。

4. Skill 与 MCP 如何配合？

答完后展开

Skill 描述任务方法和流程，MCP 提供标准化外部能力；应用按任务加载 Skill，再暴露必要 Tool。

5. Fine-Tuning、RAG、Tool/API 分别更适合什么？

答完后展开

稳定行为/任务能力可考虑微调；动态知识与引用用 RAG；实时精确数据用 Tool/API。

② 新题 1｜Spring IOC 容器有哪些方式加入 Bean？

《后端高频面试题大集合》Spring #4｜正式后端 #80

概念→原理→为什么

IoC 容器负责 Bean 的定义、创建、依赖和生命周期。原资料列出 XML、组件扫描注解、Java @Configuration/@Bean 与 @Import。

Bean 来源
├─ @Component / @Service / @Repository
├─ @Configuration + @Bean
├─ @Import
└─ XML（旧项目仍常见）

实际项目怎么用

自己控制的业务类优先组件扫描；第三方 SDK 或需要显式构造参数时常用 @Bean；框架/Starter 常用 @Import、ImportSelector 或自动配置。

AI补充/纠错：@Import 不只是“导入配置类”；框架扩展还会涉及 ImportSelector、ImportBeanDefinitionRegistrar。不要把“Bean 加入容器”只理解成 @Component。

常见坑→面试怎么说→可能追问

常见坑是扫描范围错误、同类型多 Bean 注入歧义。面试可说：Spring 最常见注册来源是组件扫描、@Bean、@Import 和 XML，业务项目与框架扩展选择不同入口。追问：@Primary/@Qualifier 怎么处理歧义？

② 新题 2｜Spring Boot 3.x 自定义 Starter

《后端高频面试题大集合》Spring #5｜正式后端 #81

概念→原理

Starter 的目标是把依赖、默认 Bean、配置属性和条件装配封装起来，让业务项目“引入依赖 + 配配置”即可使用。

starter dependency
   ↓
AutoConfiguration.imports
   ↓
@AutoConfiguration
+ @ConfigurationProperties
+ @ConditionalOn...
   ↓
业务 Bean

为什么→实际项目怎么用

例如把公司统一 Push、日志或 AI Client 封成 Starter，业务服务只配置 endpoint/key，自动配置按条件创建 Client。

AI补充/纠错：原资料说“Spring Boot 3.x 移除 spring.factories”过于宽泛。准确说法是：注册自动配置类不再使用旧的 spring.factories EnableAutoConfiguration 机制，使用 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports；spring.factories 机制本身并非所有用途都不存在。

常见坑→面试怎么说→可能追问

避免无条件抢占用户自定义 Bean，通常配合 @ConditionalOnMissingBean。追问：Starter 和 AutoConfiguration 模块是否一定是同一个 jar？如何做配置提示 metadata？

② 新题 3｜IOC 与 DI 的联系和区别

《后端高频面试题大集合》Spring #6｜正式后端 #82

概念→原理

IoC 是控制反转思想：对象创建和依赖管理从业务代码转交容器；DI 是实现 IoC 的主要方式：容器把对象需要的依赖注入进去。

IoC：谁控制对象？
业务代码 → Spring Container

DI：依赖怎么给对象？
Container → Constructor → Service

实际项目怎么用

Controller 不自己 new Service，Service 不自己 new Repository，由 Spring 根据 BeanDefinition 构造依赖图。

AI补充/纠错：现代 Spring 项目优先构造器注入：依赖显式、便于测试，也能把必需依赖设计成 final。字段注入虽然方便，但依赖隐藏且不利于普通单元测试。

面试怎么说→可能追问

一句话：IoC 是设计思想，DI 是容器实现控制反转的重要手段。追问通常进入 BeanDefinition、Bean 生命周期和循环依赖。

② 新题 4｜Agent Tool 层怎么定义、怎么被调用？

《AI应用开发面试题 / Agent / RAG》Tool Calling / MCP 1.1.7

概念→原理

原资料把 Tool 定义拆成 name、description、parameters(JSON Schema)，运行时由 Tool Registry/Dispatcher 完成查找、校验、执行和结果回注。

messages + tool schemas
 → LLM
 → tool_call(name,args)
 → Registry / Dispatcher
 → 参数校验 + 权限
 → Java Service / API
 → tool_result
 → LLM

Spring Boot / Spring AI 怎么用

Tool 可以映射到 Java 方法或 Callback；description 要清楚说明何时使用，Java 层负责参数、认证授权、超时、幂等和异常包装。

AI补充/纠错：Tool Schema 只是模型接口契约，不是安全边界。模型选择了某 Tool 也不能绕过 Java 权限校验；删除、付款等高风险 Tool 还应加入确认和审计。

常见坑→面试怎么说→可能追问

Tool 太多会增加 Token 和误选率；返回结果过大也会污染 Context。追问：1000 个 Tools 怎么处理？可用两阶段路由、语义检索 Top-K、分层动态加载。

② 新题 5｜什么是 Token？为什么工程上很重要？

《AI大模型面试题-基础篇》#32

概念→原理

Token 是 Tokenizer 把文本编码后供模型处理的基本单位，不等同于“一个字”或“一个单词”。不同模型/Tokenizer 对同一文本可能产生不同 Token 数。

Text
 ↓ Tokenizer
Token IDs
 ↓ Model
Output Token IDs
 ↓ Decode
Text

为什么→实际项目怎么用

Token 数直接影响 Context Window、延迟、显存/计算和 API 成本。RAG 中 Chunk 大小、召回数量、Chat History、Tool Schema 都会争夺同一个上下文预算。

AI补充/纠错：原资料举的“GPT-4 最大 32k”和固定中文/英文 Token 示例具有模型与版本依赖，不能当通用规律。工程上应使用目标模型对应的 tokenizer/usage 统计，不要用字符数硬猜 Token。

常见坑→面试怎么说→可能追问

不要只裁掉最旧消息而不考虑 System Prompt、Tool Schema、RAG Context 的优先级。面试可说：Token 是模型实际处理和计费的单位，我会围绕总 Context Budget 做历史压缩、检索 Top-K 和输出上限控制。追问：Token 超限怎么处理？
