① 前一天复习｜先凭记忆回答

复习 1｜Lazy Queue

为什么 RabbitMQ 4.x 面试时不应该继续把 x-queue-mode=lazy 当成核心优化方案？

答完后展开

因为 3.12 起 Classic Queue 已采用接近旧 Lazy Queue 的低内存行为，当前 4.x 已不再支持 lazy mode。现代设计应讨论 Classic、Quorum、Stream 的选择与容量治理。

面试口述版：Lazy Queue 是旧版本概念，现代 RabbitMQ 已把低内存落盘行为融入 Classic Queue，不再需要显式 lazy mode。

复习 2｜消息堆积

为什么 backlog 增加时不能只看 Queue Ready，也不能直接增加 Consumer？

答完后展开

还要看 unacked、publish/ack rate、最老消息年龄和下游 RT。若瓶颈在 DB/API，扩 Consumer 只会放大下游压力。

复习 3｜高可用

为什么“RabbitMQ 有三个节点”不等于 Queue 数据已经高可用？

答完后展开

集群节点数与 Queue 数据复制不是一回事。需要节点故障下的数据可用性，应使用具备复制机制的 Quorum Queue 等方案，并满足多数派。

复习 4｜多轮对话

Token Budget、Summary、Long-term Memory 各解决什么问题？

答完后展开

Token Budget 控制本轮上下文成本；Summary 压缩被截断历史；Long-term Memory 按当前任务检索跨窗口的重要信息。三者共同完成 Context Assembly。

复习 5｜Prompt Engineering

为什么 Prompt 优化不能只靠“感觉回答变好了”？

答完后展开

需要固定 Eval Case、成功率/准确率/相关性/延迟/成本等指标，才能比较不同 Prompt 版本并避免回归。

间隔复习｜约 3 天前

Publisher Confirm 成功是否等于 Consumer 业务成功？

答完后展开

不是。Confirm 只覆盖 Publisher 到 Broker 的发布确认；消费端仍需 ACK、幂等、事务、重试与补偿。

间隔复习｜约 7 天前

为什么 STW 和 Full GC 不能画等号？

答完后展开

STW 描述应用线程暂停；Full GC 描述一次 GC 事件/回收范围。Young、Mixed、Full 等事件都可能包含 STW 阶段。

② 新题 1｜RabbitMQ Virtual Host 有什么用途？

原资料：《后端高频面试题大集合》MQ 第11题｜PDF 第88页。正式后端 #62。

概念

Virtual Host（vhost）是 RabbitMQ Broker 内的逻辑隔离边界。Exchange、Queue、Binding、Permission 等资源都归属于某个 vhost。

原理 → 为什么

RabbitMQ Broker
├─ /app-a
│  ├─ Exchange
│  └─ Queue
└─ /app-b
   ├─ Exchange
   └─ Queue

不同 vhost 中可以存在同名资源，权限也可独立配置，因此适合做应用、租户或环境级隔离。

实际项目怎么用

例如 dev/test/prod 使用不同 vhost，或者不同业务系统分 vhost，并为应用账号只授予对应 vhost 的 configure/write/read 权限。

AI补充/纠错：vhost 是逻辑隔离与权限边界，不是物理资源隔离。不同 vhost 仍共享同一个 Broker 的 CPU、内存、磁盘和网络，因此高负载业务不能只靠 vhost 达成性能隔离。

常见坑

把 vhost 当成独立 RabbitMQ 实例；所有系统共用默认 / 且给账号过大权限；把开发与生产放同一 Broker 后误以为 vhost 能避免资源争抢。

面试口述版：RabbitMQ vhost 是 Broker 内的逻辑命名空间和权限边界，可以隔离 Exchange、Queue、Binding 和用户权限，常用于不同应用或环境。但它不是物理资源隔离，底层 Broker 资源仍共享。

可能追问

两个 vhost 能不能直接 Binding？——不能直接跨 vhost 绑定；跨边界通常需要应用转发、Federation/Shovel 等机制。

② 新题 2｜什么是顺序消息？RabbitMQ 怎么保证顺序？

原资料：《后端高频面试题大集合》MQ 第12题｜PDF 第88～89页。正式后端 #63。

概念

顺序消息要求同一业务序列中的消息按预期先后被处理。全局顺序吞吐低，实际更常见的是按订单号、用户号等业务 Key 保证局部顺序。

原理 → 为什么

orderId=1001
create → pay → ship → finish
        ↓
同一 Queue / 同一顺序消费通道

顺序真正难点不只是“Queue FIFO”，还包括多个 Producer 并发、多个 Consumer 并发、失败重试和重新入队导致的重排。

实际项目怎么用

按业务 Key 路由到固定 Queue；对需要严格顺序的 Key 控制单一消费序列；消费端使用状态机/版本号防止旧事件覆盖新状态。

AI补充/纠错：原资料“单一队列即可保证顺序”过于简化。RabbitMQ Queue 本身有顺序语义，但多消费者、优先级、redelivery/requeue、并发 Publisher 都可能影响业务观察到的处理顺序。生产系统常把“Broker 顺序”与“业务状态机幂等”一起设计。

常见坑

为了全局顺序把所有业务压成单 Consumer；重试消息重新入队后仍假设绝对顺序；没有版本号却允许并发更新订单状态。

面试口述版：顺序消息一般不追求全局顺序，而是按业务 Key 做局部顺序。RabbitMQ 可以让同一 Key 进入固定 Queue，并控制消费并发；同时业务侧用幂等、状态机和版本号处理重试或重投造成的顺序扰动。

可能追问

为什么全局顺序性能差？——因为必须减少并行度，吞吐上限会被单一串行处理链限制。

② 新题 3｜RabbitMQ Exchange 有哪些类型？

原资料：《后端高频面试题大集合》MQ 第13题｜PDF 第89～90页。正式后端 #64。

概念与原理

Exchange路由规则典型场景
DirectRouting Key 精确匹配按业务类型/级别精确路由
Fanout忽略 Routing Key，广播到所有绑定 Queue事件广播
TopicRouting Key 模式匹配，* 一段、# 多段灵活主题订阅
Headers按 Header 属性匹配不适合用 Routing Key 表达的规则

为什么

Producer 不应该知道每个 Consumer 的 Queue。它只向 Exchange 发布，由 Binding Rule 决定消息进入哪些 Queue，从而降低生产者与消费者的拓扑耦合。

实际项目怎么用

订单事件可用 Topic：order.created、order.paid；审计与通知各绑定自己需要的模式。系统级广播可使用 Fanout。

AI补充/纠错：Exchange 本身通常不负责“保存消息”，它负责路由。可靠性设计要继续考虑目标 Queue、mandatory/return、Publisher Confirm、持久化与消费确认。

常见坑

把 Fanout 当 Topic 使用；误以为 Topic 的 * 和 # 一样；Binding Key 写错却没有 Return/监控，导致 unroutable message 被忽略。

面试口述版：RabbitMQ 常见 Exchange 有 Direct、Fanout、Topic、Headers。Direct 精确匹配，Fanout 广播，Topic 按模式路由，Headers 按消息头匹配。Exchange 解决路由，不等于消息存储和端到端可靠性。

可能追问

Topic 的 * 和 #？——* 匹配一个单词，# 匹配零个或多个单词。

② 新题 4｜Agent 的 Tool Calling 机制是怎样的？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.22｜PDF 第38～39页。

概念

Tool Calling 是模型请求应用执行外部能力的机制。模型负责“决定调用什么以及生成参数”，真正执行 API/数据库/函数的是应用程序，不是模型本身。

原理

User
 ↓
LLM + Tool Schema
 ↓
tool_call{name,args}
 ↓
Java Application 执行真实 Tool
 ↓
tool_result
 ↓
LLM 继续推理 / 再调用 Tool / 最终回答

为什么

LLM 参数中不可能永久包含实时天气、数据库最新数据或“发邮件”这种外部动作。Tool 把模型的语言决策能力和确定性的业务 API 连接起来。

Spring AI 2.0 怎么用

@Tool(description = "查询订单状态")
public OrderStatus getOrderStatus(String orderId) {
    return orderService.getStatus(orderId);
}

chatClient.prompt(userText)
    .tools(orderTools)
    .call()
    .content();
AI补充/纠错（Spring AI 2.0）：当前 Spring AI 2.0 的 ChatClient 由 ToolCallingAdvisor 驱动 Tool Loop，ToolCallingManager 执行 ToolCallback；可以使用 @Tool、MethodToolCallback、FunctionToolCallback。模型没有直接获得真实 API 权限，应用层才是执行者。

常见坑

把所有危险 Tool 设成 default tools；相信模型生成的参数而不校验；删除/转账等副作用操作没有权限、幂等和确认；Tool 无限循环没有调用次数限制；Tool Result 含敏感数据却全部回传模型。

面试口述版：Tool Calling 分三层：Schema 告诉模型有哪些工具，模型根据用户意图生成结构化 tool call，应用层校验参数并执行真实函数，再把结果返回模型继续推理。Spring AI 2.0 可以用 @Tool 和 ToolCallback，并由 ToolCallingAdvisor 管理循环；真正的权限和执行控制必须在 Java 应用层。

可能追问

Tool Calling 和 MCP 什么关系？——Tool Calling 是模型调用工具的通用机制；MCP 是标准化客户端与外部 Tool/Resource Server 之间能力暴露与连接的协议，两者可以组合。

② 新题 5｜什么是大模型幻觉？怎么降低？

原资料：《AI大模型面试题-基础篇》重新编号后的专题第3题｜PDF 第21页。

概念

幻觉是模型生成了语言上合理、但事实错误、来源不存在、推理不成立或与已知上下文矛盾的内容。

原理 → 为什么

LLM 的核心目标是根据上下文预测后续 Token，并不是一个天然的事实数据库。训练数据噪声、知识过期、上下文不足、问题歧义、检索失败以及模型为了完成回答而补全细节，都可能产生幻觉。

实际项目怎么用

高质量 Prompt
+ RAG / Tool 获取真实数据
+ 强制引用来源
+ Structured Output
+ 业务规则校验
+ Confidence / Unknown
+ 高风险 Human-in-the-loop
+ Eval Dataset 持续回归

例如企业知识库问答：检索不到证据时返回“当前资料无法确认”，而不是要求模型必须给答案；订单状态则直接 Tool Call 查询数据库，而不是让模型凭上下文猜。

AI补充/纠错：降低 temperature 只能减少随机性，不能从根本上消除事实错误；RAG 也不是“装上就无幻觉”，还需要评估 Retrieval Recall、Context Relevance、Faithfulness，并防止模型脱离证据作答。

常见坑

把模型自报 confidence 当真实概率；只做 Prompt 不做数据验证；检索失败仍强制回答；把 Structured Output 误认为事实校验；高风险业务没有人工确认。

面试口述版：幻觉是模型生成看似合理但事实错误的内容，本质上与概率生成、知识覆盖和上下文质量有关。工程上我会用 RAG/Tool grounding、引用、结构化输出、业务校验、拒答机制和 Eval 来降低风险，高风险操作再加人工确认。目标是可检测、可约束、可追溯，而不是宣称完全消除幻觉。

可能追问

RAG 为什么仍会幻觉？——可能检索错、Chunk 缺信息、排序错、上下文被截断，或者模型拿到正确证据后仍做了无依据扩展，因此 Retrieval 和 Generation 两层都要评估。
