复习 1｜MQ vs RPC

什么情况下你会优先 RPC，什么情况下优先 MQ？为什么实际系统经常两者同时存在？

答完后展开

需要同步结果、强调用语义时偏 RPC；允许异步、削峰、事件解耦时偏 MQ。订单系统常用 RPC 完成库存/价格确认，再用 MQ 发订单事件驱动通知、积分等。

面试口述版：RPC 解决同步协作，MQ 解决异步事件和时间解耦；选型要看时延、一致性、失败处理和依赖关系。

复习 2｜引入 MQ 的代价

MQ 把同步调用解耦以后，为什么系统反而会多出可靠性和一致性问题？

答完后展开

消息跨进程异步传递后，会出现丢失、重复、乱序、堆积、延迟、Broker 故障、消费失败等新状态，因此需要 ACK、幂等、补偿、监控和追踪。

复习 3｜RabbitMQ 丢消息链路

从 Producer 到业务处理完成，至少有哪些位置需要保证可靠性？

答完后展开

Producer→Exchange 用 Publisher Confirm；Exchange→Queue 要确认 routing；Exchange/Queue/message 要正确持久化；Consumer 侧在业务成功后 ACK，并配合幂等与补偿。

复习 4｜Memory 精准更新

为什么明确的用户设置应该用稳定 memoryId/key 更新，而不是只靠向量相似度找旧记忆？

答完后展开

向量相似度是语义近似，不是身份约束。语言、权限、配置等精确事实应使用稳定 key 做 UPDATE/UPSERT，VectorStore 更适合语义历史。

复习 5｜AI 类型安全

Structured Output 已经成功反序列化成 Java DTO 后，还需要哪些校验？

答完后展开

还需要 Bean Validation、业务规则、权限校验和必要的事实/证据核验。Schema 正确只代表结构正确。

间隔复习｜约 3 天前

线上 CPU 100% 时，为什么只抓一次 jstack 不够？

答完后展开

单次快照可能只是瞬时状态，应结合 top/top -H、线程 ID、连续多次 jstack/jcmd 采样及 GC/业务 Trace 判断持续热点。

间隔复习｜约 7 天前

Java 有 GC，为什么 static Map 仍可能形成内存泄漏？

答完后展开

GC 判断的是可达性。static Map 仍从 GC Roots 可达时，即使对象已无业务价值也不能回收。

② 新题 1｜RabbitMQ 未开启消息持久化，重启一定会丢吗？

原资料：《后端高频面试题大集合》MQ 第5题｜PDF 第79～80页。正式后端 #56。

概念 → 原理

原资料的关键考点是：“未持久化”不等于“此刻绝对只存在于 RAM”，但也绝不能据此认为重启后可靠。 RabbitMQ/操作系统可能因为内存压力把页面换出或写盘，但这不是消息持久化语义。

为什么

durable queue / persistent message
→ 目标：Broker 重启后仍按持久化语义恢复

non-persistent message
→ 不提供重启后的可靠恢复承诺
→ 即使某时刻底层碰巧写过磁盘，也不能当可靠性保证
AI补充/纠错：原资料把“非持久化消息可能因内存紧张写入磁盘/Swap”作为“不一定丢”的解释，容易让人误解。工程上必须按语义设计：如果业务要求 Broker 重启后消息仍在，就应使用 durable queue + persistent message，并结合 Publisher Confirm；不能依赖 OS Swap 或实现细节。

实际项目怎么用

订单、支付、库存事件通常应明确配置可靠持久化；可丢的实时状态/低价值通知才考虑降低持久化成本。

常见坑

只设置消息 persistent，但 Queue 本身不 durable；或者 Queue/Message 都持久化，却没有 Confirm，Producer 仍不知道 Broker 是否真正接收。

面试口述版：未持久化消息不能获得重启后的可靠恢复保证。业务需要可靠消息时，我不会依赖 Swap 或底层偶然落盘，而会同时考虑 durable queue、persistent message、Publisher Confirm 和消费端 ACK。

可能追问

持久化是不是就 100% 不丢？——不是，还要考虑生产端确认、路由、复制/节点故障以及消费端业务事务。

② 新题 2｜RabbitMQ 如何保证消息可靠传输？

原资料：《后端高频面试题大集合》MQ 第6题｜PDF 第80～82页。正式后端 #57。

概念 → 原理

Producer
  ↓ Publisher Confirm
Exchange
  ↓ Routing / Return
Queue (durable)
  ↓ persistent message
Consumer
  ↓ business success
ACK / NACK

可靠性不是一个开关，而是一条端到端链路。原资料明确列出 Exchange/Queue/Message 持久化、confirmCallback、returnCallback 与 manual ACK。

为什么

每一跳都有独立失败窗口：Producer 发送失败、routing 不到 Queue、Broker 重启、Consumer 收到后进程崩溃、业务 DB 成功但 ACK 丢失等。

实际项目怎么用

Spring Boot 中应配合 Publisher Confirm、returns、手动/受控 ACK、幂等键、重试与死信队列；对“DB 提交 + 发消息”这种双写问题，再考虑 Outbox 或事务消息模式。

AI补充/纠错：可靠传输通常追求的是 at-least-once + 消费端幂等，而不是轻率声称 exactly-once。重复投递是可靠重试机制自然带来的结果之一。

常见坑

业务还没提交就 ACK；无限重试毒消息；没有 messageId/业务唯一键；把 Confirm 当成“消费者已处理成功”。

面试口述版：我会按 Producer→Exchange→Queue→Consumer 全链路设计可靠性：生产端 Confirm、正确 routing、Queue/Message 持久化、消费成功后 ACK，并用幂等、重试、DLQ 和补偿处理 at-least-once 带来的重复与异常。

可能追问

Confirm 成功代表什么？——代表 Broker 侧对发布结果的确认，不代表消费者业务已经成功。

② 新题 3｜什么是消息堆积？怎么定位和处理？

原资料：《后端高频面试题大集合》MQ 第7题｜PDF 第82～83页。正式后端 #58。

概念

消息堆积就是生产速率持续大于有效消费速率，导致 Queue/Topic 中待处理消息越来越多。

原理 → 为什么

原因观察点处理方向
Consumer 逻辑慢单条耗时、DB/API RT优化代码、批处理、并发
Consumer 故障/阻塞实例数、线程、错误率恢复实例、隔离故障
流量突增publish rate扩容、削峰、限流
Broker 资源不足CPU/Memory/Disk/IO扩容 Broker、调优存储
失败重试风暴retry/DLQ rate退避、限次、DLQ

实际项目怎么用

先看 backlog 增长速度，而不是只看“现在有 10 万条”。如果每分钟生产 1 万、消费 1.2 万，积压正在恢复；反过来即使当前只有 1 万条，也可能快速失控。

AI补充/纠错：不要一看到积压就盲目增加 Consumer。若瓶颈在数据库连接池、第三方 API 或单 Key 顺序约束，扩 Consumer 只会把压力推向下游。先定位瓶颈，再扩容。

常见坑

无限重试导致毒消息循环；扩 Consumer 超过 Queue/Partition 可并行上限；没有 backlog age 指标，只监控消息条数。

面试口述版：消息堆积本质是有效消费能力低于生产速率。我会先看生产/消费速率、最老消息年龄和下游 RT，判断是流量、消费者、Broker 还是重试问题，再决定扩容、优化、限流或 DLQ，不能只机械增加消费者。

可能追问

为什么“最老消息年龄”很重要？——它比单纯消息条数更直接反映用户实际等待时间和积压是否恶化。

② 新题 4｜Memory 前后不一致时如何解决？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.20“存储时如果出现前后不一致的情况如何解决？”｜PDF 第34～35页。

概念

原资料把冲突分为：时序更新、事实矛盾、并发写入冲突，并提出 Last Write Wins、LLM 合并、置信度、用户确认和多版本共存。

原理

new memory
   ↓
找到同一 memory key
   ↓
版本/时间/来源比较
   ├─ 明确更新 → replace
   ├─ 不同维度 → merge
   ├─ 无法判断 → pending_confirmation
   └─ 并发冲突 → optimistic lock / retry

为什么

“最新一句话永远覆盖旧值”并不安全。用户可能是在描述过去、引用别人，或者两个 Agent 同时写入。

实际项目怎么用｜Java / Spring

user_memory(
  user_id,
  memory_key,
  value,
  confidence,
  valid_from,
  valid_to,
  version,
  source_message_id,
  updated_at
)

UPDATE ... WHERE id=? AND version=?

明确事实用 PostgreSQL + 乐观锁；语义历史可以多版本进入 VectorStore，但检索时根据有效期、confidence、metadata 过滤。

AI补充/纠错：LLM 不应该成为数据库并发控制器。LLM 可以判断语义上是“修正还是补充”，但并发写冲突仍应由数据库 version/transaction/unique constraint 解决。高价值矛盾应保留来源并允许用户确认。

常见坑

只用 updated_at 做 LWW；旧向量不删除导致检索出互相矛盾的记忆；没有 source，之后无法追溯为什么写入。

面试口述版：Memory 冲突我会区分语义冲突和并发冲突。语义层根据 key、时间、来源和 confidence 判断 replace/merge/pending；数据库并发则用 version 乐观锁或事务保证。关键事实保留来源和版本，不能让 LLM 直接承担一致性控制。

可能追问

“我以前用 MySQL，现在用 PostgreSQL”应该覆盖还是共存？——如果是时间演进，应保留历史版本并把当前有效值指向 PostgreSQL。

② 新题 5｜AI 项目的多轮对话如何管理？

原资料：《AI大模型面试题-基础篇》在 #22“类型安全和错误处理”后进入新的专题编号，第1题“说下你在AI项目中的多轮对话如何管理？”｜PDF 第18～19页。按原资料编号保留。

概念

多轮对话不是“把所有 messages 永远塞回模型”，而是同时管理会话状态、上下文窗口、摘要、长期事实和 Token Budget。

原理

Current Query
 + System Prompt
 + Session State
 + Recent Window
 + Conversation Summary
 + Relevant Long-term Memory
 + Tool Result
 → Model

为什么

历史无限增长会增加成本和延迟，还可能让过时信息污染当前回答。原资料因此提出滑动窗口、重要性过滤、压缩总结、冷热分层、Token Budget 与会话清理。

实际项目怎么用｜Spring AI

Java 侧可以把最近消息交给 ChatMemory，把完整 Chat History 落 PostgreSQL；业务状态用结构化表保存；长期语义 Memory 进入 VectorStore；Context Assembly 由 Spring Service/Advisor 统一编排。

AI补充/纠错：“最大对话轮数”只是资源保护手段，不应该把第 N+1 轮直接当成失忆。更好的做法是窗口 + 摘要 + 结构化状态 + 按需长期检索。同时必须按 userId / conversationId / tenantId 隔离。

常见坑

把完整 History 当 Memory；摘要不断二次摘要造成信息漂移；多用户共用 conversationId；Tool Result 永久塞入长期记忆。

面试口述版：多轮对话我会分成会话状态、最近消息窗口、历史摘要和长期记忆四层，并做 Token Budget。Spring AI 中 ChatMemory 管近期上下文，完整 History 和结构化状态持久化，长期语义信息按需从 VectorStore 检索，所有数据按用户和会话严格隔离。

可能追问

窗口满了怎么办？——不是简单删除全部旧消息，而是保留关键状态，对较老历史摘要化，需要时再从持久层或长期 Memory 检索。
