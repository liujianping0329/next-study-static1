① 前一天复习｜先凭记忆回答

复习来源：2026-09-16 正式 Day 17。请先口述 20～30 秒，再展开答案；未收到实时作答，不虚构掌握评分。

复习 1｜JVM 诊断工具

jps、jstat、jstack、jcmd 各解决什么问题？为什么现代 HotSpot 排障更值得熟悉 jcmd？

答完后展开

jps 找 PID；jstat 看 GC/内存统计趋势；jstack 看线程栈；jcmd 是综合诊断入口，可做线程、GC、JFR 等操作。真正排障要按问题类型选工具，而不是机械执行命令。

面试口述版：我会先确认异常类型，再用 jcmd/jstat 看 JVM 宏观状态，CPU、死锁和阻塞问题再看线程栈，必要时结合 JFR 或 heap dump 深挖。

复习 2｜CPU 高

从 Java 进程 CPU 高到定位具体代码，完整链路是什么？为什么建议连续采样？

答完后展开

top 找 PID → top -Hp 找热点 TID → 转十六进制 → jstack/jcmd Thread.print 按 nid 定位。连续采样可区分持续热点和瞬时尖峰，并辅助判断死循环、锁竞争、GC 或高流量。

复习 3｜G1 GC 日志

看一条 GC 日志时，除了 before→after，还至少应该看哪些维度？

答完后展开

事件类型/cause、GC ID、暂停时间、频率、并发周期、Young/Mixed/Full、Humongous、回收后 live set 趋势，以及业务 p95/p99。

复习 4｜Memory 生命周期

为什么完整 Chat History、短期 ChatMemory、结构化 Profile 和语义长期 Memory 不应该放在同一层？

答完后展开

四者的读取方式、更新语义、保留期限和检索方式不同。完整历史用于审计；短期 Memory 服务当前上下文；Profile 要精确覆盖；语义长期 Memory 才适合向量检索。

复习 5｜Model IO

Prompts、Models、Parsers/Structured Output 分别解决什么？

答完后展开

Prompt 构造模型输入；Model 提供统一调用抽象；Parser/Structured Output 将文本结果转换为稳定的数据结构。编号纠错：该题在原 PDF 中是 #20。

间隔复习｜约 3 天前

STW 和 Full GC 为什么不能画等号？

答完后展开

STW 描述应用线程暂停；Full GC 描述 GC 事件/回收范围。Young、Mixed、Full 都可能包含 STW 阶段。

间隔复习｜约 7 天前

Metaspace OOM 为什么不能只增加 MaxMetaspaceSize？

答完后展开

如果根因是 ClassLoader 泄漏或动态类持续生成，加大上限只会推迟 OOM，应检查类加载数量和 ClassLoader 生命周期。

② 新题 1｜8核16G 的 Spring Boot 电商项目，JVM 参数怎么给？

原资料：《后端高频面试题大集合》JVM 第24题“电商项目服务器8核16G内存，基于JDK11+ OOM给一份JVM配置”｜PDF 第70～72页。正式后端 #50。

概念→原理

面试官真正考的是“能否从业务约束推导配置”，不是背一串参数。16G 机器不能把 16G 全给 Java Heap，还要留给 Metaspace、Direct Memory、线程栈、Code Cache、native library、容器/OS。

-Xms6g -Xmx6g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump/heap.hprof
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags:filecount=10,filesize=100M

为什么 / 实际项目怎么用

先给“安全起点”，再通过压测和生产观测调整。G1 会自适应年轻代，通常不主动指定 -Xmn。OOM dump 与 GC 日志必须提前准备，否则事故发生后证据可能已经丢失。

AI补充/纠错：原资料直接给 8G Heap、32M Region、ActiveProcessorCount=8，不应当作通用标准答案。ActiveProcessorCount 不是“ParallelGCThreads 的替代参数”；它是 JVM 用来覆盖可见 CPU 数的参数，会影响多处并行度计算。G1HeapRegionSize 一般也不需要手工固定，除非有明确证据。

常见坑

按日 UV 推导瞬时并发；把全部物理内存给 Xmx；把 MaxGCPauseMillis 当 SLA 硬保证；没有确认 dump 目录磁盘空间。

面试口述版：我不会只凭 8核16G 就给唯一参数，会先留足 native/OS 空间，例如从 6G 左右固定堆和 G1 起步，打开 GC 日志与 OOM heap dump，再根据压测的吞吐、p95/p99、GC pause、live set 和 native memory 调整。

可能追问

Xms 是否一定等于 Xmx？为什么 G1 通常不配 Xmn？容器环境怎么计算可用内存？

③ 新题 2｜生产 JVM 性能优化的方法论

原资料：《后端高频面试题大集合》JVM 第25题“说你有哪些对生产环境JVM性能优化的方法论”｜PDF 第72～73页。正式后端 #51。

概念→原理

明确业务目标
→ 建立基线
→ 观测 JVM + 应用 + 下游
→ 找瓶颈
→ 一次只改少量变量
→ 二次压测
→ 对比收益与副作用
→ 灰度 / 回滚

为什么

JVM 参数不是越“高级”越好。真正目标是业务吞吐、延迟、稳定性和成本，而不是让某个 GC 数字单独变漂亮。

实际项目怎么用

外部指标内部指标
QPS、p95/p99、错误率CPU、Heap、Allocation Rate
超时、用户等待GC pause/frequency、线程、锁
下游 SLADB pool、HTTP pool、queue
AI补充/纠错：不要看到 GC 多就先调 Heap，也不要看到 CPU 高就先加线程。JVM、代码、数据库、线程池、外部 API、网络可能互相放大问题。优化必须以测量和 ROI 为依据。

常见坑

没有 baseline；一次改十个参数；只看平均 RT；测试环境数据量和生产差异巨大；优化后不做回归。

面试口述版：我的方法是先定义业务指标并建立基线，再通过 JVM、应用和下游观测找到真正瓶颈；每轮只做可验证的修改，然后重新压测比较吞吐、p95/p99、GC、CPU 和资源成本，最后灰度上线并保留回滚方案。

可能追问

如何判断是 JVM 还是 DB？什么情况下应该换 GC？如何证明优化有效？

④ 新题 3｜Kafka、RabbitMQ、RocketMQ 怎么选？

原资料：《后端高频面试题大集合》MQ消息队列 第1题“新项目你如何选择 Kafka-RabbitMQ-RocketMQ？”｜PDF 第74页起。正式后端 #52。

概念→原理

产品优先考虑场景
Kafka高吞吐事件流、日志、数据管道、流处理生态
RabbitMQ传统消息路由、AMQP、复杂 routing、任务队列
RocketMQJava 业务消息、延迟/事务等企业消息场景，尤其团队已有生态时

为什么 / 实际项目怎么用

选型维度至少包括：吞吐与延迟、消息语义、顺序、重试/延迟、堆积、生态、运维能力、团队经验、云服务支持和迁移成本。

AI补充/纠错：原资料中“Kafka 文档较少、需要掌握 Scala”“RocketMQ 社区不活跃”等评价明显带有年代性，不能直接作为 2026 选型结论。面试重点应是需求驱动，而不是背产品优缺点排行榜。

常见坑

只按性能排行榜选；忽略运维团队；把“支持 exactly-once”理解成整个业务链天然 exactly-once；忽略消费幂等。

面试口述版：MQ 我不会先选产品再找场景，而是先看吞吐、消息语义、顺序/延迟/事务需求、堆积规模和团队运维能力。大规模事件流优先评估 Kafka，传统 AMQP 路由会看 RabbitMQ，Java 企业业务消息并已有相应生态时会评估 RocketMQ。

可能追问

为什么用了 MQ 仍要做幂等？如何处理消息积压？Kafka 的消费组解决什么？

⑤ 新题 4｜向量记忆库如何增量更新用户画像？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.18“你的向量记忆库是如何更新用户画像的？如何区分短期记忆和长期记忆？”｜PDF 第31～32页。

概念→原理

新对话
→ 提取 new / changed / confirmed
→ 与现有 Profile 比较
→ 冲突解决 + confidence
→ 精确事实 Upsert PostgreSQL
→ 语义记忆 Upsert VectorStore
→ 更新 lastSeen / mentionCount

为什么

用户画像应该增量更新，而不是每次把所有历史重新 Embedding。短期 Memory 服务当前会话；只有稳定、跨会话仍有价值的信息才沉淀为长期 Memory。

实际项目怎么用

例如“我主要写 Java”可成为结构化 profile；一次临时讨论 Python 不应立即把技术栈覆盖成 Python。建议记录 source、confidence、firstSeen、lastSeen、mentionCount、updatedAt。

AI补充/纠错：原资料示例采用“新信息覆盖旧信息”，生产上过于激进。应区分用户明确修改、模型推断、重复确认和临时上下文。Spring AI 的 ChatMemory 适合短期消息窗口；完整 Profile 的冲突规则应由 Java Service/DB 负责，而不是指望 VectorStore 自动解决。

常见坑

所有消息都长期保存；一次提及就改画像；跨 user/tenant 检索；没有删除/纠错机制；向量库保存精确开关但无法稳定覆盖。

面试口述版：用户画像我采用增量更新：从新对话提取候选变化，与现有 Profile 做冲突和置信度判断，精确事实写关系库，语义历史写 VectorStore。短期 ChatMemory 只负责当前上下文，经过筛选的稳定信息才沉淀为长期记忆。

可能追问

用户明确说“忘掉这个偏好”怎么处理？VectorStore 如何精准替换？如何防止跨租户污染？

⑥ 新题 5｜Python Typing 到 Java/Spring AI 的类型安全

原资料：《AI大模型面试题-基础篇》第21题“Python类型增强模块Typing在AI项目中的应用”｜PDF 第16～17页。原题为 Python 视角，今天转换为 Java/Spring AI。

概念→原理

原资料强调类型注解提升可读性、IDE 检查、团队协作，并用 Dict、Tuple、Union、Optional、Literal 等约束 AI 管道输入输出。Java 的对应优势是编译期静态类型更强。

public record FoodAnalysis(
    String title,
    List<FoodItem> items,
    Integer estimatedCalories
) {}

为什么 / 实际项目怎么用

AI 输出本质仍不可信。通过 Structured Output 映射成 record/DTO 后，还应使用 Bean Validation 和业务校验，把“模型返回了一段 JSON”变成“程序接受了一个合法领域对象”。

LLM
→ Structured Output
→ DTO / record
→ @Valid / 业务校验
→ Domain
→ DB / Tool
AI补充/纠错：类型安全只能保证结构，不保证事实正确。例如 calories 是 Integer，并不代表 800 kcal 就一定准确。AI 项目需要把结构验证、业务规则验证和事实验证分开。

常见坑

大量使用 Map<String,Object>；DTO 与领域模型混在一起；只验证 JSON 能解析；Optional 被滥用于字段和序列化模型。

面试口述版：Python Typing 的核心价值是让 AI 管道接口更明确；在 Java 中我会进一步利用 record/DTO、泛型、枚举、Structured Output 和 Bean Validation，把模型输出先转换成受约束的结构，再进入业务层。但类型正确不等于事实正确，事实仍需要业务或数据源校验。

可能追问

Structured Output 解析失败怎么重试？record 和 Lombok DTO 怎么选？为什么不建议全程 Map？
