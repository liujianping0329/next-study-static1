① 前一天复习｜先凭记忆回答

复习来源：2026-09-17 正式 Day 18。请先口述 20～30 秒，再展开答案；未收到实时作答，不虚构掌握评分。

复习 1｜JVM 参数

8核16G 机器为什么不能直接把 16G 全给 Xmx？G1 为什么通常不主动固定 Xmn？

答完后展开

进程还需要 Metaspace、Direct Memory、线程栈、Code Cache、native library 与 OS 空间；G1 会动态调整年轻代来满足暂停目标，固定 Xmn 可能限制其自适应能力。

面试口述版：我会先给 JVM 和 OS 留 native 空间，再以压测数据决定 Heap；G1 下通常不固定年轻代，而是让收集器根据暂停目标动态调整。

复习 2｜性能优化

为什么生产 JVM 优化必须先有 baseline，而且一次不应该改十几个参数？

答完后展开

没有基线就无法证明收益；一次修改太多变量会失去因果关系，也很难回滚。应围绕 p95/p99、QPS、GC、CPU、资源成本逐轮验证。

复习 3｜MQ 选型

Kafka、RabbitMQ、RocketMQ 的选型为什么不能只比较“谁吞吐最高”？

答完后展开

还要考虑消息语义、顺序、路由、延迟/重试、堆积、生态、运维能力、团队经验和迁移成本。

复习 4｜Memory 画像

用户画像为什么更适合“增量更新”，而不是每轮对话全量重新生成？

答完后展开

增量更新能保留稳定事实、降低成本并减少画像漂移；应记录 key、confidence、last_seen、mention_count 等信息并处理冲突。

复习 5｜类型安全

为什么模型输出成功映射成 Java record，仍然不能证明内容正确？

答完后展开

类型/Schema 只能保证结构约束，不能保证事实正确、业务规则正确。还需要 Bean Validation、业务校验和必要的证据核验。

间隔复习｜约 3 天前

ZGC “不分代”为什么已经是旧答案？

答完后展开

现代 JDK 的 ZGC 已进入分代实现，旧资料描述的是早期 non-generational ZGC，面试要明确版本。

间隔复习｜约 7 天前

不同 ClassLoader 为什么可以让同名 User 成为两个不同类型？

答完后展开

JVM 的类身份由二进制类名和 defining ClassLoader 共同决定，因此不同 defining ClassLoader 加载的同名类并不相同。

② 新题 1｜什么时候用 MQ，什么时候用 RPC？

原资料：《后端高频面试题大集合》MQ 第2题“什么时候应该用MQ，什么时候应该用RPC调用？”｜PDF 第75～76页。正式后端 #53。

概念 → 原理

RPCMQ
同步请求/响应为主异步事件/任务为主
调用方通常需要立即结果生产者不必等待消费者完成
直接依赖服务契约通过消息契约解耦

为什么 / 实际项目怎么用

登录 → 权限服务 → 需要立即结果 → RPC
注册成功 → 发邮件/推送 → 可异步 → MQ
下单 → 查询库存是否可卖 → RPC
订单已创建 → 积分/通知/分析 → MQ
AI补充/纠错：原资料把“RPC 可在同一进程直接调用、无需网络开销”混入 RPC 描述，不严谨。RPC 通常指 Remote Procedure Call，本质就是跨进程/网络调用；同进程方法调用不叫 RPC。另外“MQ 比 RPC 可靠”也不是绝对结论，二者都需要超时、重试、幂等、熔断或持久化等工程保证。

常见坑

为了“解耦”把所有调用改成 MQ；需要立即返回业务结果却强行异步；RPC 无限重试导致雪崩；MQ 没设计最终一致性和补偿。

面试口述版：需要即时结果、强调用语义时我优先 RPC；允许异步、需要削峰或事件解耦时优先 MQ。实际系统经常两者结合，关键是根据一致性、时延、失败处理和依赖关系选择。

③ 新题 2｜引入 MQ 会带来哪些新问题？

原资料：《后端高频面试题大集合》MQ 第3题“业务项目的架构里面引入MQ消息队列，可能带来哪些问题？”｜PDF 第76～77页。正式后端 #54。

概念 → 原理

MQ 降低了时间耦合，但同时把“一个同步调用失败”变成一组分布式状态问题。

Producer → Broker → Consumer
   │          │          │
 发送失败    堆积/故障    重复/失败
              ↓
      一致性 + 可观测性 + 运维复杂度

实际项目怎么用

问题工程对策
消息丢失Confirm、持久化、ACK、补偿
重复消费业务幂等、唯一键、消费记录
消息堆积Lag 监控、扩消费者、限流、降级
乱序业务 key 分区/单队列、版本号
最终一致性Outbox/事务消息、对账、补偿
排障困难messageId、traceId、指标与告警
AI补充/纠错：资料列出的丢失、重复、堆积、延迟、可用性、版本兼容都正确，但面试最好继续回答“怎么治理”，否则只说明知道风险，没有体现生产经验。

常见坑

认为 MQ 天生 exactly-once；消费者失败无限重试；没有死信/停车场策略；没有 lag 告警；消息 Schema 随意破坏兼容性。

面试口述版：MQ 带来的核心成本是可靠性、一致性和运维复杂度。我会重点治理消息丢失、重复、堆积、乱序和最终一致性，并通过幂等、ACK、重试/死信、监控和补偿机制把风险显式化。

怎么做消费幂等？消息堆积时先扩容还是先限流？

④ 新题 3｜RabbitMQ 消息会在哪些环节丢失？

原资料：《后端高频面试题大集合》MQ 第4题“说下RabbitMQ消息丢失的场景有哪些和怎么解决？”｜PDF 第77～78页。正式后端 #55。

概念 → 原理

Producer
  ↓ Publisher Confirm
Exchange
  ↓ Routing / Return
Queue (durable + persistent message)
  ↓ Consumer Ack
Consumer business

四个重点失效点

① Broker 持久化：队列/消息未正确持久化，Broker 故障可能丢失。
② Producer → Broker：发送后未确认，可使用 Publisher Confirm 判断 Broker 是否接收。
③ Exchange → Queue：Routing 失败，需要处理 returned message / mandatory 等机制。
④ Consumer：业务尚未成功就 ACK，进程随后崩溃会造成业务层面的丢失；应根据处理结果决定 ACK/NACK。

AI补充/纠错：“deliveryMode=2 就绝对不会丢”是错误理解。可靠消息需要 durable queue、persistent message、Publisher Confirm、正确 routing、consumer ACK，以及业务侧幂等/补偿共同保证。持久化和确认机制也不能代替业务事务一致性。

实际项目怎么用

@RabbitListener(...)
try {
    // 1. 幂等检查
    // 2. 执行业务事务
    // 3. 成功后 ACK
} catch (RetryableException e) {
    // NACK / retry
} catch (Exception e) {
    // DLQ / parking lot / 人工补偿
}
面试口述版：我会沿 Producer→Exchange→Queue→Consumer 整条链路分析丢失点：生产端用 Confirm，路由失败要可感知，Broker 侧保证队列和关键消息持久化，消费端在业务成功后再 ACK，同时必须做幂等和补偿，因为可靠投递不等于业务 exactly-once。

Confirm 和 Return 各解决什么？ACK 应该在 DB commit 前还是后？如何解决 DB 成功但 ACK 失败？

⑤ 新题 4｜Agent Memory 能否精准替换指定片段？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.19“记忆更新时能否精准替换指定片段，还是需要全量清空重建？”｜PDF 第32～33页。

概念 → 原理

答案是：可以精准更新，而且通常应该精准更新。原资料给出 Key 定向 upsert、语义匹配更新和版本化更新三种思路。

memory_id = userId + memoryType + key

新事实
 → 按稳定 key 找旧记录
 → 冲突判断
 → 更新 value / embedding / metadata
 → version + 1
 → 保留 updatedAt / source

为什么 / 实际项目怎么用

例如用户把“首选语言 Java”改为“Kotlin”，不应该清空他的饮食偏好、项目背景等全部 Memory。结构化事实优先按稳定 ID 在 PostgreSQL 精确 UPDATE；只有需要语义召回的描述才同步更新 VectorStore embedding。

AI补充/纠错：原资料示例把 profile 直接放 Vector DB，可以实现，但对于语言、开关、地区、权限等需要精确覆盖的事实，关系数据库通常更合适。不要用 similarity threshold 作为唯一的“是不是同一事实”判断；最好先有稳定 memory key，再用语义匹配处理无 key 的自由文本记忆。

什么时候全量重建

用户明确要求重置；Schema/Embedding 模型重大迁移；画像严重污染且无法可靠合并。即使重建，也应考虑审计、版本和可回滚性。

面试口述版：Memory 更新我优先使用稳定 memoryId 做精准 upsert，而不是全量重建。结构化 Profile 在关系库精确更新，语义记忆同步更新向量；对无法确定 key 的文本才先做语义匹配。只有用户重置、Schema 大迁移或画像严重污染时才考虑全量重建。

⑥ 新题 5｜AI 项目的类型安全与错误处理

原资料：《AI大模型面试题-基础篇》#22“说下你在AI项目中的类型安全和错误处理”｜PDF 第17～18页。

概念 → 原理

原资料从 Python typing、TypeVar/NewType、mypy 与外部数据检查展开。Java / Spring AI 中可以把它升级为“编译期类型 + 运行时输入校验 + LLM 输出 Schema + 业务校验 + 异常分类”。

HTTP JSON
 → DTO / Bean Validation
 → Domain Service
 → ChatClient
 → Structured Output
 → Java record
 → Schema / Business Validation
 → Domain Result

实际项目怎么用

record FoodAnalysis(
    String title,
    Integer calories,
    Double protein
) {}

FoodAnalysis result = chatClient.prompt()
    .user(prompt)
    .call()
    .entity(FoodAnalysis.class);

// 结构成功后仍需业务校验
if (result.calories() != null && result.calories() < 0) {
    throw new InvalidAiOutputException();
}
AI补充/纠错：Spring AI 2.0.1 的 .entity(Type.class) 可把模型输出映射为 Java 类型，并支持 Schema validation / provider-native structured output；但官方仍强调结构化输出不是事实正确性的保证。外部输入、模型输出、Tool Result 都属于不可信边界，必须继续做校验。

错误分类

错误处理
400/输入非法不重试，直接返回可理解错误
429/临时 5xx有限次数指数退避 + jitter
Schema 不符校验/有限重试/降级
Tool 业务失败按业务语义补偿，不盲目重试
事实不可信证据校验/人工确认/拒绝自动执行
面试口述版：AI 项目的类型安全不能只靠模型按 JSON 输出。我会在 API 输入、Java DTO、模型 Structured Output、Tool Result 和业务 Domain 每一层做类型与业务校验，并把可重试的网络错误、不可重试的输入错误和高风险业务错误分开处理。
