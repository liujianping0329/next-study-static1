复习 1｜Mark-Compact

先回答：Mark-Compact 为什么能解决 Mark-Sweep 的外部碎片？它付出的主要代价是什么？

答完后展开

它在标记存活对象后会移动对象并压缩到一端，因此形成连续空闲空间；代价是对象搬迁、引用更新以及对应暂停/并发协调成本。

面试口述版：Mark-Compact 通过移动存活对象获得连续空间，解决 Mark-Sweep 的外部碎片，但要付出对象搬迁和引用更新成本。

复习 2｜分代收集

先回答：分代思想真正依赖的假设是什么？为什么不能把“分代”简单等同于固定 Eden/S0/S1/Old 物理布局？

答完后展开

核心是多数对象生命周期短、少数对象长期存活，因此对不同生命周期采用不同回收策略。G1 等现代收集器可以使用动态 Region 承担年轻代/老年代角色，所以分代是策略思想，不等于固定连续布局。

复习 3｜Partial / Full GC / STW

先回答：为什么 STW 不能和 Full GC 画等号？

答完后展开

Partial/Full 描述收集范围或事件类型；STW 描述应用线程被暂停。Young GC、Mixed GC、Full GC 都可能包含 STW 阶段。

复习 4｜Cursor Memory

先回答：Project Rules、代码检索、短期聊天历史和长期 Memory 为什么应该分层？

答完后展开

稳定规则需要确定性注入；代码知识适合按需检索；近期对话属于短期上下文；跨会话偏好/决策才适合长期持久化。混在一起会造成 Token 浪费、更新困难和上下文污染。

复习 5｜PromptTemplate

先回答：PromptTemplate 能不能代替 Java 侧的 SQL 白名单、ACL 和 Tool 权限控制？为什么？

答完后展开

不能。Prompt 是给模型的软指令，可能被误解或受到注入攻击；安全边界必须由 Java 程序、权限系统和校验器强制执行。

间隔复习｜约 3 天前：GC 泄漏

为什么“业务上已经没用”的对象仍可能无法被 GC？

答完后展开

只要从 GC Roots 仍可达，GC 就必须认为它存活。典型来源包括 static Collection、ThreadLocal、Listener、Cache 和 ClassLoader。

间隔复习｜约 7 天前：CompletableFuture

为什么生产环境不应把所有慢 I/O 都直接扔进 commonPool？

答完后展开

共享池会让不同业务互相争抢线程；慢 I/O 还可能长时间占用 worker。应使用隔离的业务 Executor，并结合下游 DB/API 容量、超时和限流设计。

② 新题 1｜什么是垃圾收集器？常见收集器怎么选？

原资料：《后端高频面试题大集合》JVM 第 18 题“什么是垃圾收集器和常用的垃圾收集器组合”｜PDF 第 60～61 页。正式后端 #44。

概念

GC 算法是方法论，垃圾收集器是这些思想在具体 JVM 中的工程实现。HotSpot 历史上出现过 Serial、Parallel、CMS、G1、ZGC 等不同方案。

原理

收集器主要目标典型理解
Serial简单、低资源小堆/资源受限场景
Parallel吞吐量并行 STW 回收
G1吞吐与暂停平衡Region + 并发标记 + Evacuation
ZGC极低暂停高度并发、面向低延迟

为什么

不存在“永远最强”的 GC。批处理更关心吞吐，在线 API 更关心 p95/p99，超大堆且极度敏感暂停的系统可能更偏向 ZGC。

实际项目怎么用

先让 JVM 默认选择并压测，再根据业务目标看 GC pause、allocation rate、live set、CPU、吞吐和尾延迟，而不是先抄一套参数。

AI补充/纠错

AI补充/纠错：资料中的 CMS/ParNew 组合属于历史知识；CMS 已在 JDK 14 移除。现代面试重点应转向 G1 与 ZGC。Oracle 当前 JDK 文档也建议根据吞吐与暂停目标选收集器，而不是背固定组合。

常见坑

把“收集算法”和“收集器”混为一谈；把 JDK 8 的默认组合当成现代 JDK 通用结论；只看平均暂停，不看 p99。

面试口述版：GC 算法是方法论，垃圾收集器是具体实现。现代 HotSpot 中我重点关注 G1 和 ZGC：G1 适合大多数服务端场景，ZGC 更偏极低暂停。选择时我会以吞吐、p95/p99、堆大小和 CPU 成本做压测，而不是认为某个收集器绝对最好。

可能追问

G1 为什么成为默认？Parallel 和 G1 的目标差异？CMS 为什么被淘汰？

③ 新题 2｜G1 为什么叫 Garbage-First？

原资料：《后端高频面试题大集合》JVM 第 19 题“介绍下新一代垃圾收集器G1收集器原理”｜PDF 第 61～63 页。正式后端 #45。

概念

G1 把堆划分成多个 Region，Region 可以动态承担 Eden、Survivor、Old 等角色。它不是把整个老年代一次性处理，而是按回收收益和成本挑选更值得回收的 Region。

Heap
├─ Region A : Eden
├─ Region B : Old
├─ Region C : Survivor
├─ Region D : Humongous
└─ ...

原理

核心流程可理解为 Young GC、并发标记和 Mixed GC。并发标记识别各 Region 的存活情况，后续在暂停预算内优先选择回收价值较高的 Region，并把存活对象 evacuation 到其他 Region。

为什么

Region 化让 GC 不必总是一次处理完整连续老年代，可以更细粒度地规划回收工作，从而更容易围绕暂停时间目标做取舍。

实际项目怎么用

-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-Xlog:gc*

MaxGCPauseMillis 是目标而不是硬实时保证。调优时要一起看 Young/Mixed GC、Humongous allocation、concurrent cycle 是否来得及以及 Full GC 是否发生。

AI补充/纠错

AI补充/纠错：原资料写“约 2048 个 Region、1～32MB”适合旧版本理解，不应作为所有现代 JDK 的固定事实。Region 大小由 JVM 根据堆规模选择，也可以通过 G1HeapRegionSize 影响。另一个易错点是 Humongous：不要死背资料中的“超过 1.5 个 Region”，应以当前 JVM 对 Humongous 的实际阈值定义为准。

常见坑

把 G1 Region 当成固定 Young/Old 分区；认为 MaxGCPauseMillis 能保证绝不超时；看到 Full GC 只加 Xmx 而不看 allocation/live set。

面试口述版：G1 的核心是 Region 化和按收益优先回收。它保留分代思想，但 Young/Old 是 Region 的动态角色。并发标记后，G1 根据垃圾量和预计回收成本，在暂停目标内挑选高收益 Region 做 evacuation，所以叫 Garbage-First。

可能追问

Mixed GC 是什么？Humongous 对象为什么麻烦？Remembered Set 解决什么问题？

④ 新题 3｜ZGC 的定位与现代版本变化

原资料：《后端高频面试题大集合》JVM 第 20 题“介绍下新一代垃圾收集器ZGC原理和特点”｜PDF 第 63～64 页起。正式后端 #46。

概念

ZGC 是 HotSpot 面向低延迟设计的可伸缩并发垃圾收集器，尽量把昂贵工作与应用线程并发执行，使暂停时间与堆大小弱相关。

原理

理解重点是并发标记、并发转移以及通过 barrier / 指针元数据等机制在对象移动期间维持引用正确性，而不是死背某一版 Region 尺寸。

为什么

G1 已经能较好控制暂停，但对于非常严格的尾延迟目标，大量对象搬迁如果集中在 STW 内仍可能过长。ZGC 把更多工作并发化，用额外 CPU/复杂度换更低暂停。

实际项目怎么用

java -XX:+UseZGC -Xms4g -Xmx4g -Xlog:gc* -jar app.jar

适合低延迟 API、大堆服务等候选场景，但仍需真实压测 CPU、吞吐和内存 headroom。

AI补充/纠错

AI补充/纠错：这是今天最重要的版本纠错：原资料写“ZGC 不分代”，对旧版本成立，但当前 Oracle JDK 25 文档明确说明：从 JDK 24 起 ZGC 就是分代式 GC，ZGenerational 选项已经移除。因此现代面试不能再回答“ZGC 的特点是不分代”。

常见坑

继续背“ZGC 永远不分代”；认为低暂停等于零暂停；只追求低延迟却忽略 CPU 和内存余量。

面试口述版：ZGC 是面向低延迟的大量并发 GC，把标记和对象转移等重工作尽量与应用线程并发执行。需要特别注意版本变化：JDK 24 起 ZGC 已经是分代式收集器，所以旧资料里“不分代”的描述已经过时。

可能追问

ZGC 与 G1 怎么选？为什么并发 GC 需要更多 heap headroom？JDK 24 的 Generational ZGC 变化是什么？

⑤ 新题 4｜Memory 上下文记忆的处理逻辑

原资料：《AI应用开发面试题 / Agent / RAG》1.1.16“Memory 上下文记忆功能的处理逻辑”｜PDF 第 29～30 页。

概念

资料把 Memory 分成长期 RAG、短期上下文压缩，以及机械模式/智能模式。核心不是“存得越多越好”，而是让当前任务拿到最相关、可信且成本可控的信息。

原理

短期：最近消息 → Window / Summary
长期：候选事实 → 提取/去重 → DB / VectorStore
读取：Current Query → 相关记忆检索 → Context Assembly

为什么

全量历史会持续吃 Token，而且旧信息可能与新事实冲突。机械窗口成本低且确定；智能摘要/检索质量更好，但增加模型调用成本和延迟，因此生产通常混合使用。

实际项目怎么用

Spring AI 2.0.1 中可以使用 MessageWindowChatMemory 管短期窗口，并通过 MessageChatMemoryAdvisor 注入 ChatClient；语义长期记忆可使用 VectorStore 方案。每次调用都必须提供 conversation ID，并应由服务端按 user/session 派生，避免跨用户污染。

AI补充/纠错

AI补充/纠错：资料把“Token 超过 70～80% 就压缩”写成经验值，不能当框架固定规则。Spring AI 默认 MessageWindowChatMemory 是按消息窗口管理；如果需要 Token-based summary，应自己实现策略。另外 ChatMemory 不等于完整 Chat History，审计历史应另存 Spring Data/PostgreSQL。

常见坑

固定 conversationId 导致串用户；把所有历史都向量化；摘要不断摘要导致事实漂移；把完整审计历史塞 ChatMemory。

面试口述版：Memory 我会分短期和长期。短期用窗口加必要摘要控制 Token；长期先提取稳定事实，再按结构化数据或语义内容分别落数据库和 VectorStore。读取时只召回当前任务相关内容。Spring AI 可用 ChatMemory/Advisor 管短期上下文，但完整聊天历史要独立持久化，并按 user/session 做严格隔离。

可能追问

摘要漂移怎么解决？Memory 冲突怎么覆盖？conversationId 为什么必须服务端生成？

⑥ 新题 5｜LangChain Model IO 链路如何映射到 Spring AI？

原资料：《AI大模型面试题-基础篇》第 18 题“LangChain的大模型IO交互链路是怎样的？主要包含哪些环节？”｜PDF 第 14～15 页。

概念

原资料把 Model IO 分为输入、Prompt、模型调用、输出处理四层，本质上是一次 LLM 请求从业务输入到可用业务结果的完整数据通路。

User Input
→ Validate / Normalize
→ Prompt Assembly
→ Model Call
→ Structured Output / Validation
→ Business Response

原理

输入层负责校验与上下文准备；Prompt 层组合 system/user/memory/RAG；模型层调用 Provider；输出层负责结构化转换、验证、异常处理和业务落地。

为什么

如果把 AI 调用写成一个裸 String prompt → String answer，权限、重试、可观测性、结构化输出和错误处理都会散落在业务代码里，很难维护。

实际项目怎么用

Controller
  ↓ validate
Service
  ↓
ChatClient.prompt()
  + System/User Template
  + Memory Advisor
  + RAG Advisor
  ↓
ChatModel
  ↓
Structured Output / Validator
  ↓
Domain Object

Spring AI 的 Advisor Chain 很适合承载 Memory、RAG、日志、安全检查等横切逻辑。

AI补充/纠错

AI补充/纠错：这题虽然写 LangChain，但核心概念与语言无关。Java 项目没必要为了 Model IO 再引入 FastAPI/LangChain；Spring AI 的 ChatClient、PromptTemplate、Advisor、ChatModel、Structured Output 已经能覆盖主链路。安全校验仍应放在 Java 确定性代码里。

常见坑

Controller 直接拼 Prompt；把模型返回 JSON 当绝对可信；重试没有预算导致成本爆炸；RAG/Memory 无用户隔离。

面试口述版：Model IO 可以拆成输入预处理、Prompt 组装、模型调用和输出后处理。Java/Spring AI 中我会用 ChatClient 作为入口，PromptTemplate 组织输入，Advisor 组合 Memory/RAG 等横切能力，ChatModel 调 Provider，最后用结构化输出和业务校验把结果转成领域对象。

Advisor 顺序为什么重要？Structured Output 失败怎么办？Tool Calling 属于 Model IO 哪一层？
