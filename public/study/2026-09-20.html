复习 1｜非持久化消息

为什么“消息可能被操作系统写到磁盘”不等于“RabbitMQ 重启后消息可靠”？

答完后展开

可靠性看的是 Broker 提供的持久化语义，而不是某个时刻底层页面是否碰巧落盘。需要重启恢复时，应设计 durable queue、persistent message、Publisher Confirm 等完整链路。

面试口述版：不能把 Swap 或底层偶然落盘当持久化保证，可靠消息必须按 RabbitMQ 的持久化与确认语义设计。

复习 2｜可靠传输

Publisher Confirm 成功是否代表 Consumer 已经处理成功？为什么？

答完后展开

不是。Confirm 是发布端与 Broker 之间的确认；消费端业务是否成功还要依赖 ACK/NACK、业务事务、幂等、重试与补偿。

复习 3｜消息堆积

为什么看到 backlog 增加不能第一反应就是“多加几个 Consumer”？

答完后展开

真正瓶颈可能在 DB 连接池、第三方 API、锁竞争或顺序消费。盲目扩 Consumer 可能把压力继续传给下游，应先比较生产/消费速率、最老消息年龄与下游 RT。

复习 4｜Memory 冲突

LLM 为什么不应该负责数据库并发控制？

答完后展开

LLM 可以辅助判断语义上是修正还是补充，但并发写一致性应由 transaction、version、optimistic locking、unique constraint 等确定性机制保证。

复习 5｜多轮对话

为什么多轮对话管理不是“把所有历史 messages 一直塞进 Prompt”？

答完后展开

上下文窗口和成本有限，历史还可能含无关/过期信息。生产系统应使用滑动窗口、摘要、重要性筛选、长期记忆检索与 Token Budget。

间隔复习｜约 3 天前

RabbitMQ、Kafka、RocketMQ 选型为什么不能只看吞吐量？

答完后展开

还要看路由模型、顺序/事务需求、可靠性、延迟、团队经验、运维成本与生态。

间隔复习｜约 7 天前

Mark-Sweep 和 Mark-Compact 的核心差异是什么？

答完后展开

Mark-Sweep 清理垃圾但不移动存活对象，容易产生外部碎片；Mark-Compact 会移动并压缩存活对象，获得连续空间，但增加对象移动和引用更新成本。

② 新题 1｜RabbitMQ Lazy Queue 与普通队列有什么区别？

原资料：《后端高频面试题大集合》MQ 第8题｜PDF 第84～85页。正式后端 #59。

概念

原资料基于旧版 RabbitMQ：Lazy Queue 尽量把消息放到磁盘，需要消费时再加载，从而降低长队列的内存占用；普通 Classic Queue 则更积极保留消息在内存。

原理 → 为什么

旧版思路：
普通 Classic Queue → 更多消息驻留内存 → 低延迟但长队列吃内存
Lazy Queue          → 主要落盘 → 内存稳定但增加磁盘 I/O
AI补充/纠错（重要版本差异）：这道原题已经明显过时。RabbitMQ 3.12 起 Classic Queue 的行为已经接近过去的 Lazy Queue，x-queue-mode=lazy 被忽略；当前 RabbitMQ 4.x 已不再支持 lazy mode。现代 Classic Queue 只保留少量消息在内存，其余主要写盘。Quorum Queue 也不使用 lazy mode。

实际项目怎么用

新项目不要再通过 .lazy() 作为解决长队列的核心方案。先确定是否需要复制与高数据安全：需要高可用时优先考虑 Quorum Queue；非复制场景才考虑 Classic Queue，并通过容量、磁盘、TTL、max-length、消费能力等治理积压。

常见坑

把旧教程里的 x-queue-mode=lazy 当成 RabbitMQ 4.x 最佳实践；或者以为“写盘”本身就等于“高可用复制”。

面试口述版：历史上 Lazy Queue 用磁盘换低内存，适合长队列。但 RabbitMQ 3.12 后 Classic Queue 已采用类似低内存策略，lazy mode 已被废弃并在当前版本不再支持，所以现代设计更应该讨论 Classic、Quorum 和 Stream 的选择，而不是继续配置 lazy queue。

可能追问

消息都写盘后是不是一定高可用？——不是。持久化解决单节点重启恢复的一部分问题，复制与多数派机制才是节点故障下高可用的关键。

② 新题 2｜RabbitMQ 消息堆积有哪些解决方案？

原资料：《后端高频面试题大集合》MQ 第9题｜PDF 第85～86页。正式后端 #60。

概念 → 原理

原资料给出两个主要方向：使用 Lazy Queue 扩大可承受的堆积量，以及增加 Consumer/Work Queue 并发提高消费速度。

为什么

Backlog 变化率 ≈ Publish Rate - Consume Rate

要让积压下降：
1. 降低生产速率
2. 提高有效消费速率
3. 临时扩大可承受容量
4. 消除失败重试/下游瓶颈

实际项目怎么用

先看 publish rate、deliver/ack rate、ready/unacked、oldest message age、Consumer utilization，再定位 DB/API/线程池/磁盘。确认消费者确实可水平扩展后再增加实例；必要时限流 Producer、隔离毒消息、调整 prefetch，并建立 DLQ。

AI补充/纠错：原资料把 Lazy Queue 当方案一，这是旧版本思路。RabbitMQ 3.12+ 已不再需要显式 lazy mode。现代重点是容量规划、Classic/Quorum 类型选择、磁盘能力、max-length/TTL、Consumer 扩容与下游保护。

常见坑

只扩 Consumer 不看 DB；无限提高并发导致连接池耗尽；把未 ACK 的慢处理误判成 Queue Ready 积压；为了“清积压”跳过幂等和顺序约束。

面试口述版：消息堆积本质是生产速率长期大于有效消费速率。我会先用 ready/unacked、生产消费速率和最老消息年龄定位，再根据瓶颈做消费者扩容、业务优化、下游保护、限流和容量治理，而不是直接无脑加消费者。

可能追问

如果数据库已经满载怎么办？——不能继续扩 Consumer，应先保护 DB，可限流、降低消费并发、批处理或优化 SQL/索引，再逐步消化 backlog。

② 新题 3｜RabbitMQ 高可用集群怎么设计？

原资料：《后端高频面试题大集合》MQ 第10题｜PDF 第86～87页。正式后端 #61。

概念

原资料比较“普通集群”和“镜像队列”：普通集群共享元数据但 Queue 消息主要位于特定节点；镜像队列把消息复制到多个节点。

原理 → 为什么

高可用的核心不是“有多个 RabbitMQ 节点”本身，而是关键 Queue 数据是否有复制，以及发生节点故障后是否能选出仍包含一致数据的可用副本。

AI补充/纠错（重要版本差异）：Classic Mirrored Queues 已在 RabbitMQ 4.0 完全移除。现代需要复制、高数据安全的队列应优先使用 Quorum Queue（或适合日志流场景的 Streams）。Quorum Queue 使用多数派机制；例如 3 个成员可以容忍 1 个成员不可用。原资料“镜像队列保证 100% 不丢”的说法也不应作为严谨结论。

实际项目怎么用

3 节点 RabbitMQ Cluster
        ↓
Quorum Queue：3 members
        ↓
允许 1 个成员故障仍保持 quorum
        ↓
客户端配置多个地址 / LB + 自动恢复
        ↓
Publisher Confirm + Consumer ACK + 幂等

常见坑

只搭 3 个 Broker 却仍使用非复制 Classic Queue；把 Load Balancer 当数据复制；Quorum Queue 成员越多越好；跨高延迟 WAN 强行做同一个 quorum。

面试口述版：现代 RabbitMQ 高可用我会优先用 Quorum Queue，而不是旧的 Classic Mirrored Queue，因为后者在 4.0 已移除。通常用奇数成员形成多数派，例如 3 成员容忍 1 个故障，同时客户端配置多节点连接恢复，并继续配合 Confirm、ACK、幂等和监控。

可能追问

3 个 Broker 就一定高可用吗？——不一定；如果 Queue 是非复制 Classic Queue，节点挂掉时该 Queue 数据仍可能不可用。

② 新题 4｜Agent 多轮对话如何实现？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.21“多轮对话的实现方案”｜PDF 第35～36页。

概念

多轮对话的核心不是保存一个 List，而是持续构建“当前这一轮最有效的上下文”。原资料方案包含追加消息、Token 预算、从新到旧选择消息、历史摘要、压缩以及 Redis 持久化。

原理

Current Query
 + Recent Messages
 + History Summary
 + Relevant Long-term Memory
 + Tool Results
 + System Rules
        ↓
Context Assembly
        ↓
ChatModel

为什么

无限追加历史会增加成本、延迟和噪声，甚至让旧信息压过当前意图。因此需要“窗口 + 摘要 + 检索”的组合。

实际项目怎么用｜Java / Spring AI

conversationId
  ↓
MessageWindowChatMemory   // 最近窗口
  + PostgreSQL            // 完整 history / summary
  + VectorStore           // 相关长期记忆
  + Tool Result
  ↓
ChatClient + Advisors
AI补充/纠错：原资料中的 max_tokens * 0.6、80% 触发压缩、保留最近 5 轮都只是示例，不应写死为通用标准。生产系统还要处理 userId/tenantId 隔离、并发轮次顺序、摘要漂移、Tool Result 生命周期和隐私删除。

常见坑

conversationId 不隔离导致串话；摘要不断摘要造成事实漂移；把所有 Tool Result 永久保存；多实例服务只把会话存在本机内存。

面试口述版：多轮对话我会按 conversationId 隔离会话，短期使用滑动窗口，较早历史做摘要，长期事实按需从数据库或 VectorStore 检索，再与当前 Tool Result 一起组装上下文。Spring AI 可用 ChatMemory/Advisor 做短期窗口，但完整 History 和长期 Memory 应分层持久化。

可能追问

服务重启怎么办？——短期内存只是缓存，重要会话历史与摘要要持久化到 Redis/PostgreSQL 等外部存储。

② 新题 5｜AI 项目里的 Prompt 工程怎么设计？

原资料：《AI大模型面试题-基础篇》“多轮对话”专题第2题｜PDF 第19～20页：“如何设计Prompt工程在AI项目开发中的应用”。

概念

原资料把 Prompt Engineering 定义为通过结构化输入引导模型完成任务，并强调角色、任务、格式、约束四个要素。

原理 → 为什么

Role      → 模型以什么身份工作
Task      → 具体要完成什么
Context   → 当前任务需要哪些事实
Constraint→ 什么不能做 / 范围是什么
Output    → 结果必须长什么样
Example   → 必要时提供 few-shot 示例

实际项目怎么用｜Spring AI

把稳定 System Prompt、动态 User 参数、RAG Context 和 Tool 描述分开管理；模板放版本控制，关键任务建立固定 Eval 数据集。需要机器消费的输出优先使用 Structured Output，而不是仅靠“请严格输出 JSON”。

AI补充/纠错：原资料提到用 STAR 原则描述任务，可作为表达方式，但不是 Prompt 的强制标准。更重要的是任务边界、上下文质量、输出 Schema 和可评测性。另外 Prompt 中写“禁止访问某数据”不是安全控制，真正 ACL/Tool 权限必须由 Java 代码强制执行。

常见坑

一个超长 System Prompt 塞全部规则；Prompt 与业务代码强耦合；只凭人工感觉改 Prompt、不做回归 Eval；把安全边界寄托在自然语言指令；模板变量未经边界设计导致 Prompt Injection 扩散。

面试口述版：Prompt 工程不是单纯写一句好提示词，而是把 Role、Task、Context、Constraint 和 Output Schema 模块化，并进行版本管理和 Eval。Spring AI 中我会把 System/User Prompt、RAG、Tool 和 Structured Output 分层，真正的权限和业务约束仍由 Java 代码保证。

可能追问

怎么判断 Prompt 改好了？——用固定 Eval Case 对准确率、任务成功率、格式通过率、Token、延迟和成本做版本对比，而不是只看几个手工样例。
