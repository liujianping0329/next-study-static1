② 新题 1｜本地缓存 vs 分布式缓存

《后端高频面试题大集合》分布式缓存 #1｜正式后端 #86

白话

缓存把反复查询的昂贵结果放到更快的位置。选本地还是分布式，核心看是否需要跨实例共享，以及能接受多大的一致性复杂度。

本地分布式
位置JVM 内独立服务，如 Redis
延迟最低有网络成本
共享每实例独立多实例共享
容量受堆限制可独立扩容
Request → Caffeine → Redis → DB

项目

多 Pod 商品服务的商品详情通常放 Redis；很少变化的代码表可放 Caffeine。做两级缓存时还要处理各 Pod 的 L1 失效。

AI补充/纠错：除速度与共享，还要考虑一致性、容量、网络故障、序列化和运维。缓存不是越多越好。

追问

两级缓存如何一致？消息通知、版本号、短 TTL。Redis 故障？限流降级，避免 DB 被冲垮。哪些数据不适合？低复用、强实时一致、频繁变化的大对象。

30秒：本地缓存延迟最低但每实例独立；Redis 有网络成本但可共享和独立扩容，选型看共享、一致性、容量和故障模型。
一句话：本地换低延迟，分布式换共享与治理。

② 新题 2｜Cache-Aside 与一致性

《后端高频面试题大集合》分布式缓存一致性高频题｜正式后端 #87

白话

DB 是真相源，Cache 是副本。一次写跨两个系统，没有天然原子事务，因此目标是控制不一致窗口。

读：Cache miss → DB → 回填 Cache
写：Update DB → Delete Cache
后续读：miss → DB → 重建

常见先更新 DB 再删缓存。若先删缓存再更新 DB，并发读更容易在 DB 更新前把旧值重新写回。

AI补充/纠错：Cache-Aside 通常是最终一致，不是强一致。固定 sleep 的“延迟双删”也不能证明并发一定结束；严格场景要考虑版本号、可靠事件/CDC 或串行化。

项目

商品价格提交 DB 后删除缓存；删除失败进入可靠重试。结算仍以权威 DB/价格服务为准。

追问

删除失败？重试、消息、CDC。TTL 能强一致吗？不能，只限制错误副本寿命。为什么不只写 Redis？缓存必须可从权威源恢复。

30秒：Cache-Aside 读 miss 查 DB 回填，写常见更新 DB 后删缓存；它是最终一致方案，重要业务配可靠重试、CDC 或版本控制。
一句话：DB 是真相，Cache 是可重建副本。

② 新题 3｜缓存穿透、击穿、雪崩

《后端高频面试题大集合》分布式缓存故障治理｜正式后端 #88
问题本质治理
穿透查不存在数据空值缓存、Bloom Filter、参数校验
击穿单热点 Key 失效互斥重建、逻辑过期、主动刷新
雪崩大量 Key 或缓存整体失效TTL 抖动、多级缓存、限流降级、高可用
热点 Key 过期 → 大量请求同时 miss → DB 压力激增
互斥重建 → 只让一个请求查 DB 并重建
AI补充/纠错：Bloom Filter 可能假阳性且需要维护；分布式锁也要超时和 owner 校验。

追问

Bloom Filter 为何不能证明一定存在？可能假阳性。空值缓存代价？占空间且新增真实数据时短暂不可见。整体故障为何危险？大量流量同时压 DB。

30秒：穿透是查不存在；击穿是单热点失效；雪崩是大量 Key 或整个缓存失效。
一句话：穿透看没有，击穿看热点一个，雪崩看一大片。

② 新题 4｜MCP Server 很多怎么管理？

《AI应用开发面试题 / Agent / RAG》Tool Calling/MCP 1.1.9

白话

昨天解决“很多 Tools 怎么选”；Server 多时还要管理服务发现、连接、健康、权限、租户和故障。

User → Host/Agent
→ domain + tenant + permission
→ MCP Registry / Gateway
→ 选择少量 Server
→ Tool Retrieval / Top-K
→ LLM Tool Call
→ MCP Server → Backend

Tool Routing 解决“模型看哪些工具”；MCP 管理还解决 Server 在哪里、是否健康、谁能调用和失败如何隔离。

AI补充/纠错：Gateway、Registry、分组、动态激活是合理工程策略，但不要把路线图能力当成所有 MCP 实现已经统一具备的强制标准。

Java/Spring AI

应用层维护 MCP Client/Server Registry，先按 tenant/domain 过滤 Server，再选候选 ToolCallback；执行端必须再次鉴权。

追问

Registry vs Gateway？目录元数据 vs 请求入口治理。Server 挂了？健康检查、超时、熔断、fallback。权限？检索前过滤 + 执行端强校验。

30秒：MCP 很多时先用 Registry/Gateway 按权限和健康选 Server，再做 Tool Retrieval，只暴露少量候选，执行端再次鉴权。
一句话：先选 Server，再选 Tool，最后再鉴权。

② 新题 5｜向量数据库作用与选型

《AI大模型面试题-基础篇》#34

白话

Embedding 把语义变成高维数字。RAG 要找语义上最像的文本，向量检索系统负责做高维近邻搜索，再取回文本和 metadata。

Document → Chunk → Embedding → Vector Store
Question → Query Embedding → ANN + ACL Filter
→ Top-K → Rerank/MMR → LLM

原资料列 Milvus、FAISS、Pinecone、Chroma。真正选型应看规模、QPS/延迟、metadata 过滤、索引、更新、高可用、托管/自建、成本和运维。FAISS 更准确地说是向量相似度搜索库，而不是完整分布式数据库服务。

Spring AI 项目

Document doc = new Document(text,
    Map.of("tenantId", tenantId, "fileId", fileId));
vectorStore.add(List.of(doc));

企业 RAG 要让 tenant/file/permission 等 metadata 随 Chunk 入库，在 Retrieval 阶段先做 ACL 过滤。

AI补充/纠错：产品能力会变化，生产选型要按当前版本压测；向量库不能替代订单、库存、金额等权威实时业务 DB/API。ANN 用少量召回损失换性能，之后可 rerank 提精度。

追问

HNSW vs IVF？图索引 vs 聚类/倒排候选。Embedding 模型升级为何常需重建？向量空间可能不同。metadata filter 为什么仍不等于完整 ACL？权限继承、撤权和执行端校验仍需业务设计。

30秒：向量数据库/检索系统存 Embedding 并做高维近邻检索，是 RAG 的语义召回层；选型看规模、延迟、过滤、索引、高可用、成本和运维，实时精确数据仍走 DB/API。
一句话：向量库找语义上像的候选，不替代业务数据库。
