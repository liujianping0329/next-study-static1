复习 1｜Collector 选型

G1 和 ZGC 的主要目标差异是什么？为什么不能说某个 GC 永远最好？

答完后展开

G1 更强调吞吐与可控暂停的平衡；ZGC 更强调极低暂停。选型还取决于堆规模、CPU、吞吐、p95/p99 和实际压测。

复习 2｜G1

为什么叫 Garbage-First？Region 和传统固定 Young/Old 分区有什么区别？

答完后展开

并发标记后会评估 Region 的垃圾量和回收成本，在暂停预算内优先处理收益高的 Region；Region 的 Eden/Survivor/Old 角色可以动态变化。

复习 3｜ZGC

旧资料“ZGC 不分代”为什么现在不能直接背？

答完后展开

现代 ZGC 已进入分代实现，因此版本相关的 GC 结论必须注明 JDK 范围。

复习 4｜Agent Memory

Chat Memory 和完整 Chat History 为什么要区分？

答完后展开

Memory 是给当前模型上下文使用的有限信息；History 是完整审计/展示记录。前者要压缩和淘汰，后者通常持久化到独立数据层。

复习 5｜Model IO

Spring AI 中 Prompt、Model、Structured Output 分别对应 Model IO 的哪一段？

答完后展开

Prompt 负责构造输入，ChatModel/ChatClient 负责模型调用，Structured Output 将结果映射为 Java 结构。

间隔复习｜约 3 天前

为什么 GC Roots 可达不等于对象对业务仍有价值？

答完后展开

GC 只判断引用可达性，不理解业务语义；无用对象仍被 static/ThreadLocal/Cache 等引用时仍无法回收。

间隔复习｜约 7 天前

JVM 的方法区为什么不能简单等于 Metaspace？

答完后展开

方法区是 JVM 规范的逻辑概念，Metaspace 是 HotSpot JDK8+ 对类元数据存储的具体实现机制。

② 新题 1｜常用 JVM 诊断命令有哪些？

原资料：《后端高频面试题大集合》JVM 第21题“你知道哪些JVM常用的命令，说下使用场景”｜PDF 第65～66页。正式后端 #47。

概念与原理

工具用途
jps快速找 Java PID
jstat观察堆、GC 等统计变化
jstack线程栈、死锁、热点线程定位
jinfo查看 VM 参数，部分 manageable 参数可动态调整
jcmd现代 HotSpot 综合诊断入口，线程、GC、JFR、NMT 等

为什么 / 项目怎么用

先确认 PID
→ 看资源异常类型
→ jcmd/jstat 看 JVM 宏观状态
→ jstack/Thread.print 看线程
→ 必要时 JFR / heap dump 深挖

AI补充/纠错

AI补充/纠错：原资料主要列 jps/jinfo/jstat，现代生产排障建议把 jcmd 放在更核心位置。不要为了“会命令”机械执行会产生大文件或明显停顿的诊断动作；先评估线上影响。

常见坑

只截一份线程栈就下结论；跨 JDK 版本混用诊断工具；把 jstat 某一瞬间的数值当趋势。

面试口述版：我通常用 jps 找进程，jstat 看 GC 趋势，jstack 或 jcmd Thread.print 看线程，jinfo 看参数；现代 HotSpot 我更偏向 jcmd 作为统一诊断入口，复杂性能问题再结合 JFR。

jcmd 和 jstack 的关系？什么时候抓 heap dump？JFR 适合解决什么问题？

③ 新题 2｜线上 Java 进程 CPU 过高怎么排查？

原资料：《后端高频面试题大集合》JVM 第22题“生产环境的JVM导致CPU占用过高，说下排查思路”｜PDF 第66～68页。正式后端 #48。

概念→原理

top 找高 CPU Java PID
→ top -Hp PID 找高 CPU 线程 TID
→ printf '%x\n' TID 转十六进制
→ jstack PID / jcmd PID Thread.print
→ 按 nid=0x... 找线程栈
→ 对照代码、锁、GC、死循环、序列化等定位

为什么

“Java 进程 CPU 高”只是现象，真正消耗 CPU 的是线程；所以必须从进程下钻到线程，再从线程映射到 Java stack。

实际项目怎么用

建议连续采样多次，确认同一线程是否持续热点，同时看 GC 日志、请求量、线程池和下游异常，避免把瞬时尖峰误判成代码死循环。

AI补充/纠错

AI补充/纠错：jstack 不是“诊断内存泄漏”的首选工具。CPU/死锁/线程阻塞它很强；堆内存泄漏应更多依赖 heap dump、GC Roots、Dominator Tree。生产上还可用 JFR 做低开销持续分析。

常见坑

只看进程不看线程；十进制 TID 没转成 nid 对应的十六进制；只抓一次快照；忽略 GC 自身也可能造成高 CPU。

面试口述版：CPU 高我会先 top 确认进程，再 top -Hp 找热点线程，把线程 ID 转成十六进制后在 jstack/jcmd 的 nid 中定位调用栈，并连续采样确认。之后再区分死循环、锁竞争、GC、线程池或高流量等根因。

可能追问

如果热点线程是 GC Thread 怎么办？如果 CPU 不高但 RT 很高怎么查？

④ 新题 3｜怎么看新版 G1 GC 日志？

原资料：《后端高频面试题大集合》JVM 第23题“解读下面新版JVM垃圾GC日志参数”｜PDF 第68～69页。正式后端 #49。

概念→原理

[24.575s][info][gc] GC(0) Pause Young ... 240M->238M(528M) 5.888ms
│        │     │     │        │             │
时间     级别  标签  GC编号   事件类型       前->后(总量) + 耗时

为什么

单看“发生了 GC”没有意义，真正要结合 cause、回收前后占用、暂停时间、GC 频率和并发周期判断是否异常。

实际项目怎么用

现代 JDK 使用 Unified Logging，例如 -Xlog:gc*。重点观察 Young/Mixed/Full、Humongous allocation、concurrent cycle、pause p95/p99，以及回收后 live set 是否持续上涨。

AI补充/纠错

AI补充/纠错：资料把某些 Concurrent Cycle 行直接称为 Mixed GC 不够严谨。并发标记周期和后续 Mixed Collection 是相关但不同的概念；解日志必须按事件名称和收集器版本判断，不能只靠内存前后差。

常见坑

只看单条日志；认为 MaxGCPauseMillis 是硬保证；只看平均暂停；看到 Humongous 就直接扩大堆。

面试口述版：GC 日志我先看时间、GC ID、事件类型和 cause，再看回收前后内存与暂停时间；然后放到时间序列里看频率、p95/p99、并发周期和 Full GC。现代 JDK 我使用 -Xlog:gc* 的 Unified Logging。

可能追问

Young GC 和 Mixed GC 的区别？什么是 Humongous Allocation？如何判断内存泄漏趋势？

⑤ 新题 4｜Agent Memory 的完整生命周期怎么设计？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.17“如何进行记忆管理，怎么处理长上下文，怎么进行持久化，后续怎么读取和关联？”｜PDF 第30～31页。

概念→原理

采集消息
→ 短期 Memory
→ 提取稳定事实 / 摘要
→ 结构化存储 + 语义存储
→ 新 Query 到来
→ 按 user/tenant 检索
→ Context Assembly
→ 过期、冲突、删除、更新

为什么

完整聊天记录、模型当前需要的上下文、稳定用户画像、语义长期记忆的生命周期不同，混成一个表或一个 VectorStore 会导致 Token 膨胀、冲突难处理和权限风险。

Java / Spring AI 怎么用

MessageWindowChatMemory → 当前窗口
Redis/JDBC ChatMemoryRepository → 短期持久化
PostgreSQL → 用户画像、摘要、审计历史
VectorStore → 可语义检索的长期记忆
Spring Service → 提取、冲突解决、TTL、删除与组装

AI补充/纠错

AI补充/纠错：原资料的 70%/90% token 阈值是示例策略，不是行业标准。Spring AI 当前明确区分 Chat Memory 与完整 Chat History；MessageWindowChatMemory 默认 20 条只是默认值，也不是最佳实践常数。所有 Memory 检索必须带 conversation/user/tenant 边界。

常见坑

把所有历史都塞 Prompt；把精确用户事实只存向量库；新偏好无条件覆盖旧偏好；忘记删除/过期机制；跨租户检索。

面试口述版：我会把 Memory 生命周期拆成采集、压缩提取、持久化、检索关联、更新淘汰五步。Spring AI 的 ChatMemory 管当前上下文窗口，结构化画像放 PostgreSQL，语义长期记忆放 VectorStore，再由 Java 服务按 user、session、tenant 和 Token Budget 组装上下文。

可能追问

怎么解决新旧记忆冲突？如何实现用户要求“忘掉这件事”？Tool Result 要不要长期保存？

⑥ 新题 5｜跨平台兼容：从 LangChain 转成 Java / Spring AI 怎么理解？

原资料：《AI大模型面试题-基础篇》第19题“在使用LangChain开发项目时，如何处理跨平台兼容性问题？”｜PDF 第15页。

概念

原题聚焦 Windows/Linux/macOS 的路径、环境激活、依赖安装差异。换成 Java 项目后，核心目标仍是：同一份代码在开发机、CI、容器和生产环境可重复构建、可重复运行。

原理→为什么

Path API / Resource 抽象
+ 固定 JDK
+ Maven/Gradle Wrapper
+ BOM / lock 依赖
+ 环境变量
+ Docker
+ CI 多环境测试
= 降低平台差异

实际项目怎么用

不要手写 C:\xxx 或依赖本机目录；使用 Path、classpath/resource、配置属性和环境变量。Spring AI 的模型 Key、数据库地址、VectorStore 配置通过 profile/环境变量注入，不提交进源码。

AI补充/纠错

AI补充/纠错：“Docker 解决跨平台”也不是绝对的：CPU 架构 amd64/arm64、本地文件系统大小写、换行、时区、locale、原生库仍可能产生差异，所以 CI 和目标运行环境测试仍不可少。

常见坑

硬编码路径；依赖系统默认编码/时区；开发机 JDK 与 CI/生产不同；秘密写进 application.yml；只在 Windows 测试。

面试口述版：跨平台的核心是消除对本机环境的隐式依赖。Java/Spring 项目我会用 Path/Resource 抽象路径，Wrapper 和 BOM 固定构建依赖，固定 JDK，通过环境变量管理配置，并用 Docker 与 CI 验证目标平台；同时注意 CPU 架构、时区和文件系统差异。
