① 前一天复习｜先凭记忆回答

来源：2026-09-24 正式 Day 25。先口述，再展开答案。

1. Kafka Consumer

为什么 poll 到消息不等于业务已经可靠消费？

答完后展开

poll 只代表客户端取得记录；可靠性取决于业务处理成功与 offset commit 的边界。业务失败却提前提交 offset，会形成业务层面的丢消息。

2. Rebalance

为什么 Rebalance 不是免费的自动负载均衡？

答完后展开

它可能带来消费暂停、延迟抖动、本地状态重建与重复处理。

3. Kafka 堆积

Consumer 已经等于 Partition 数时，为什么不能继续盲目扩 Consumer？

答完后展开

额外 Consumer 会空闲，还必须确认 DB/API 等下游是否才是真瓶颈。

4. MCP

Host、Client、Server 分别承担什么角色？

答完后展开

Host 是 AI 应用；Client 在 Host 内连接 MCP Server；Server 暴露 Tools、Resources、Prompts 等能力。

5. RAG

为什么企业 RAG 的 ACL 应在 Retrieval 阶段做？

答完后展开

无权限 Chunk 一旦进入模型上下文就扩大泄露面，权限必须在检索阶段强制过滤。

间隔复习

DLX 本身是死信队列吗？Publisher Confirm 成功等于 Consumer 业务成功吗？

答完后展开

DLX 是交换机，负责重新路由死信，真正存储的是 Queue。Confirm 只确认 Publisher→Broker，不代表消费端业务事务成功。

② 新题 1｜Apache Pulsar 核心架构

《后端高频面试题大集合》MQ #23｜PDF 105～108页｜正式后端 #74

概念

Pulsar 是分布式消息与流平台。原资料介绍 Topic、Namespace、Producer、Consumer、Partition，以及 Broker、BookKeeper、ZooKeeper。

原理

Producer / Consumer
        ↓
 Broker（服务、路由、分发）
        ↓
 BookKeeper（持久化）
        ↑
 Metadata Store（协调与元数据）

为什么

Broker 与持久化存储解耦，服务层和存储层可以分别扩展。

实际项目怎么用

多租户、大规模 Topic、跨集群或希望计算存储分离时可纳入选型，同时考虑团队生态和运维成本。

AI补充/纠错：原资料把 ZooKeeper 写成固定核心组件已经过时。2026 当前 Pulsar 应理解为 Broker + BookKeeper + Metadata Store；ZooKeeper 仍支持，但新集群推荐 Oxia。

常见坑

把 Broker 当最终存储；把 ZooKeeper 当永远不可替换；只比较吞吐。

面试怎么说：Pulsar 的 Broker 负责服务与分发，BookKeeper 负责持久化，Metadata Store 负责元数据和协调；当前新集群推荐 Oxia。

可能追问

Pulsar 与 Kafka 架构差异？可先从 Pulsar 的服务层/存储层分离讲起。

② 新题 2｜Pulsar Tenant 与 Namespace

《后端高频面试题大集合》MQ #24｜PDF 108～109页｜正式后端 #75

概念

Tenant 是高层多租户边界；Namespace 位于 Tenant 内，进一步组织 Topic、权限与策略。

原理

Tenant: commerce
 ├─ Namespace: order-prod
 └─ Namespace: notify-prod

为什么

让多个团队共享集群的同时保留清晰的逻辑治理边界。

实际项目怎么用

可按组织/平台划 Tenant，再按业务域和环境划 Namespace。

AI补充/纠错：逻辑隔离不等于物理隔离；底层 Broker、BookKeeper、网络等仍可能共享，应结合权限、配额和必要的物理隔离。

常见坑

粒度过细、命名无规范、只做名称隔离却没做认证授权。

面试怎么说：Tenant 是高层多租户边界，Namespace 是 Tenant 内更细的业务和策略边界，Topic 位于 Namespace 下。

可能追问

和 RabbitMQ VHost 类似吗？都是逻辑隔离，但层级模型与底层架构不同，不能简单等价。

② 新题 3｜Spring Bean Scope

《后端高频面试题大集合》Spring #1｜PDF 110页｜正式后端 #76

概念

Scope 决定 Bean 实例生命周期。默认是 singleton，即每个 Spring IoC Container 中一个 Bean Definition 通常对应一个实例。

原理

singleton   → 容器内共享
prototype   → 每次获取创建
request     → HTTP Request
session     → HTTP Session
application → ServletContext
websocket   → WebSocket

为什么 / 项目怎么用

无状态 Service/Repository 通常使用 singleton；不要在 singleton 成员字段保存每个请求/用户的可变状态。

AI补充/纠错：原资料的 Global Session/Global Request 属于旧 Portlet 语境。当前 Spring 官方常用内建 Scope 如上。另一个坑是 prototype 普通注入 singleton 时只在 singleton 创建时解析一次；需要动态新实例可用 Provider/ObjectProvider。

常见坑

误以为 Spring singleton 是 JVM 全局单例；误以为 singleton 自动线程安全。

面试怎么说：Spring 默认 singleton；prototype 每次获取创建；Web 环境还有 request、session、application、websocket。Scope 描述生命周期，不自动保证线程安全。

可能追问

Singleton Bean 一定线程安全吗？不一定，关键看是否存在共享可变状态。

② 新题 4｜MCP 和 Skill 的区别

《AI应用开发面试题 / Agent / RAG》Tool Calling / MCP 1.1.5

概念

MCP 是标准化外部能力连接协议；Skill 更偏可复用的任务知识、行为指南、Prompt 与执行方法。

原理

MCP   → 外部能力如何发现、连接、调用
Skill → 某类任务应该怎样完成

为什么 / 项目怎么用

Java/Spring AI 中，真实数据库/API 操作放 Tool/MCP 边界；编码规范、业务步骤、领域工作流放 Skill/Prompt 层，并按任务加载。

AI补充/纠错：“Skill 一定比 MCP 占更多 Token”不是绝对规律。上下文占用取决于 Skill 长度、Tool 数量、Schema 复杂度以及是否按需加载。

常见坑

把 Skill 当权限边界；把 MCP 当 Agent；一次注入全部 Skill 和 Tool Schema。

面试怎么说：MCP 解决外部能力标准化连接，Skill 解决任务知识与行为指导。谁更占上下文没有绝对答案，生产上应动态加载当前任务需要的内容。

可能追问

Skill 能替代 MCP 吗？不能，真实外部操作仍需要 Tool/API/MCP 等执行通道。

② 新题 5｜RAG Embedding 性能与缓存

《AI大模型面试题-基础篇》RAG #30｜PDF 25～26页

概念

Embedding 会消耗算力、API 额度与时间；相同且未变化文本重复生成向量属于浪费，因此应结合缓存和增量索引。

原理

Chunk
 ↓ text hash + model/version
Cache
 ├─ Hit  → reuse embedding
 └─ Miss → EmbeddingModel → cache + VectorStore

为什么

知识库大量内容长期不变，重新发布时只需为新增或变化 Chunk 重新生成向量。

实际项目怎么用

Spring AI ingestion service 可用 textHash + embeddingModel + modelVersion + dimensions 识别缓存，只对变化内容重新 Embedding 并 upsert VectorStore。

AI补充/纠错：缓存不能只用原始文本做 Key。模型、版本、维度、Chunk/清洗规则变化时应失效并重建。原资料的“快 10～100 倍”属于示例，不应当固定性能承诺。

常见坑

模型升级仍复用旧向量；文档删除但 VectorStore 残留；Chunk 策略变化却未重建索引。

面试怎么说：Embedding 优化重点是批量、缓存、增量索引；缓存身份必须包含文本和模型版本信息，模型或分块策略变化时正确失效。

可能追问

为什么不能永久缓存？因为模型和预处理变化会改变向量语义空间。
