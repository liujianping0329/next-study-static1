① 前一天复习｜先凭记忆回答

复习 1｜Kafka Partition

Partition 为什么同时影响 Kafka 的吞吐、并行度和顺序性？

答完后展开

Partition 是 Topic 的数据分布与并行基本单元；同一 Partition 内有顺序，而同一 Consumer Group 内一个 Partition 同一时刻只交给一个 Consumer，因此 Partition 数也约束消费并行度。

面试口述版：Kafka 的扩展单位本质上是 Partition，它同时决定数据分布、局部顺序和 Consumer Group 的最大有效并行度。

复习 2｜Consumer Group

Topic 有 3 个 Partition，却启动同组 10 个 Consumer，会发生什么？

答完后展开

最多只有 3 个 Consumer 能同时拿到 Partition，其余会空闲；所以扩 Consumer 前要先看 Partition 数与下游瓶颈。

复习 3｜Producer

Kafka Producer 为什么要 Batch？有 Key 时通常如何影响 Partition？

答完后展开

Batch 减少网络请求与系统调用、提高吞吐；Key 常用于稳定映射相关事件到同一 Partition，从而获得该 Key 的分区内顺序。

复习 4｜MCP vs Function Calling

为什么说 Function Calling 是模型调用工具的能力，而 MCP 更偏标准化连接协议？

答完后展开

Function Calling 解决模型如何表达“我要调用哪个工具和参数”；MCP 则标准化 Host/Client/Server 之间如何发现和访问 Tools、Resources、Prompts 等能力。

复习 5｜RAG

什么场景应该优先 Tool/API，而不是 RAG？

答完后展开

实时价格、账户余额、订单状态等需要精确实时数据时优先 Tool/API；RAG 更适合文档型、知识型、可检索证据场景。

间隔复习｜约 3 天前

Tool Calling 中为什么“模型生成了合法 JSON”仍不能直接执行删除、支付等操作？

答完后展开

Schema 正确只代表结构合法，不代表用户有权限或业务条件满足；Java 执行层仍必须做 ACL、参数校验、幂等、审计和高风险确认。

间隔复习｜约 7 天前

JVM 调优为什么不能只改参数，不建立 baseline？

答完后展开

没有 baseline 就无法判断优化是否真正改善 p95/p99、吞吐、CPU、GC 等指标，也无法排除业务流量变化造成的假象。

② 新题 1｜Kafka Consumer 如何接收消息？

原资料：《后端高频面试题大集合》MQ 第20题｜PDF 第98～100页。正式后端 #71。

概念

Kafka Consumer 采用客户端主动拉取（pull/fetch）思路，从分配给自己的 Partition 获取数据。Consumer Group 决定 Partition 如何在组内消费者之间分配。

原理

Consumer Group
   ↓ Join / Assignment
Consumer ← assigned Partitions
   ↓ fetch
Broker / Partition Leader
   ↓ records
Consumer poll()
   ↓ business processing
Offset commit

为什么用 Pull

Consumer 能按照自己的处理能力控制拉取节奏；Broker 不需要猜测每个 Consumer 的处理速度。没有数据时也可通过等待参数减少空轮询。

实际项目怎么用

Spring Kafka 中重点不是“收到就算成功”，而是把 poll、业务事务、offset 提交之间的边界设计清楚。数据库写入失败时不能错误提交 offset，否则会形成业务丢消息。

AI补充/纠错：原资料把 RangeAssignor 写成固定默认策略属于版本敏感知识。面试更稳妥的说法是：Kafka 支持多种 Partition Assignment Strategy，具体默认值和 Consumer Group Protocol 会随客户端版本演进，生产上应查看实际客户端配置，不把某个默认策略背成永久规则。

常见坑

poll 间隔过长导致组成员被认为失效；业务处理慢却一次拉取过多；把“拉到消息”和“业务处理成功”混为一谈；offset 提交时机错误。

面试口述版：Kafka Consumer 主动从分配给自己的 Partition 拉取数据，Consumer Group 负责分区分配。消费可靠性的关键不只是 pull，而是业务处理和 offset commit 的边界；处理失败时不能错误推进 offset。

可能追问

为什么不直接 Broker Push？——Push 很难统一适配不同 Consumer 的处理能力，慢 Consumer 更容易被压垮；Pull 让消费端掌握节奏。

② 新题 2｜Kafka Rebalance 是什么？

原资料：《后端高频面试题大集合》MQ 第21题｜PDF 第100～101页。正式后端 #72。

概念

Consumer Group 成员或订阅 Partition 发生变化时，需要重新确定“哪个 Consumer 负责哪些 Partition”，这就是 Rebalance / 分区重新分配。

原理

10 Partitions + 2 Consumers
        ↓
新增 Consumer C3
        ↓
Group Coordination
        ↓
重新计算 Partition Assignment
        ↓
C1 / C2 / C3 获得新的 Partition 集合

为什么

Kafka 需要在扩容、缩容、故障和 Partition 变化时恢复组内负载分配，否则离开的 Consumer 所负责的 Partition 将无人处理。

实际项目怎么用

Kubernetes 滚动发布、实例频繁重启、处理时间超过阈值，都可能带来 Rebalance。生产上要关注 Consumer Lag、Rebalance 次数/耗时、poll 时间以及实例稳定性。

AI补充/纠错：Rebalance 不是“越多越好”的负载均衡动作。频繁 Rebalance 会造成暂停、缓存重建、重复处理风险和延迟抖动。现代 Kafka 的 Consumer Group 协议持续演进，目标之一就是减少传统全量重平衡的停顿与协调成本。

常见坑

频繁扩缩容；长时间阻塞 Consumer 线程；没有正确处理 revoke/assign 生命周期；以为 Rebalance 后旧 Consumer 的本地状态仍天然有效。

面试口述版：Rebalance 是 Consumer Group 在成员或 Partition 变化时重新分配 Partition 的过程。它保证故障恢复和水平扩展，但也会带来消费暂停和重复处理风险，所以生产上要尽量减少无意义的频繁 Rebalance。

可能追问

新增 Consumer 一定提升吞吐吗？——不一定；还受 Partition 数、下游 DB/API、CPU 与业务处理速度限制。

② 新题 3｜Kafka 海量消息堆积怎么处理？

原资料：《后端高频面试题大集合》MQ 第22题｜PDF 第101页起。正式后端 #73。

概念

消息堆积本质上是生产速率长期大于有效消费速率。先定位瓶颈，再决定扩 Consumer、增 Partition、优化业务、限流还是临时迁移积压数据。

原理 → 排查顺序

Producer Rate
     ↓
Kafka Topic / Partition
     ↓  Lag / Oldest Age
Consumer
     ↓
Thread Pool / DB / API / CPU / IO

为什么

只看“积压条数”不够：100 万条小消息可能很快清完，也可能因为单条处理 2 秒需要很久。要同时看生产速率、消费速率、Lag 增长趋势和最老消息年龄。

实际项目怎么用

先确认是不是 Consumer 挂掉或下游变慢；若 Partition 足够可扩 Consumer；若并行度受 Partition 限制，可评估增加 Partition；如果 DB 已饱和，则应先优化/限流，不能继续盲目扩 Consumer。

AI补充/纠错：增加 Partition 是有成本且可能影响 Key 到 Partition 的映射与既有顺序假设，不能把它当无副作用的紧急按钮。处理积压期间还必须保证消费幂等，因为重试、故障恢复和 offset 管理都可能导致重复处理。

常见坑

只加 Consumer 不看 Partition；下游 DB 已满仍继续扩容；临时 Topic 搬运后没有审计/回切方案；忽略重复消费与业务顺序。

面试口述版：Kafka 堆积先看生产/消费速率和 Consumer Lag，再定位是 Consumer、Partition 并行度还是下游资源瓶颈。Partition 足够时可扩 Consumer；并行度不足再评估扩 Partition；下游饱和则先优化或限流，并始终保证幂等。

可能追问

Consumer 已经等于 Partition 数怎么办？——先确认下游瓶颈；若确实需要更高 Kafka 并行度，再评估增加 Partition 或临时分流方案。

② 新题 4｜MCP 协议的核心内容

原资料：《AI应用开发面试题 / Agent / RAG》Tool Calling / MCP 专题 1.1.4｜PDF 第41～42页。

概念

MCP（Model Context Protocol）是 AI 应用连接外部工具与上下文能力的标准协议。核心角色是 Host、Client、Server。

原理

Host（AI 应用）
  └─ MCP Client
       ↓ capability / protocol negotiation
       ↓ JSON-RPC over transport
     MCP Server
       ├─ Tools
       ├─ Resources
       └─ Prompts

为什么

没有标准协议时，每个 Agent 都要为 GitHub、数据库、文件系统等能力写私有适配层；MCP 把能力发现、调用和传输接口标准化，降低 N×M 集成成本。

实际项目怎么用

Spring AI 2.0.1 可以同时作为 MCP Client 和 Server；Java 项目可用 MCP Client Starter 消费外部 Server 的工具，也可以用 @McpTool、@McpResource、@McpPrompt 暴露 Spring Service 能力。

AI补充/纠错：原资料把某一时点的“四大能力”和行业数据写得很具体，但 MCP 仍在快速演进，不应把版本能力清单背成永久规范。面试应抓住 Host/Client/Server、能力协商、Tools/Resources/Prompts、JSON-RPC 与 Transport 这些稳定核心。Spring AI 2.0 已支持 stdio、Streamable HTTP、Stateless Streamable HTTP 等多种传输。

常见坑

把 MCP 当成模型；认为接上 MCP 就自动安全；一次注入过多工具 Schema；忽略 OAuth、用户级权限、审计与 Server 信任边界。

面试口述版：MCP 是 AI 应用连接工具和上下文能力的标准协议，核心是 Host、Client、Server。Server 暴露 Tools、Resources、Prompts 等能力，Client 负责协商、发现和调用。Spring AI 可以同时做 MCP Client 和 Server，但权限与危险操作控制仍要由应用层负责。

可能追问

MCP 与 Function Calling 什么关系？——Function Calling 更偏模型如何提出工具调用；MCP 更偏工具如何标准化暴露、发现和连接，两者可以组合。

② 新题 5｜RAG 系统核心技术链路与关键组件

原资料：《AI大模型面试题-基础篇》RAG 第29题｜PDF 第24～25页。

概念

RAG 不是单一 VectorStore，而是一条从知识摄取到检索再到生成的完整数据链路。

原理

Documents / DB / Web
  ↓ Loader / Parser
  ↓ Clean + Chunk
  ↓ Embedding
  ↓ VectorStore + Metadata
  ↓ Retriever
  ↓ Filter / Hybrid / Rerank
  ↓ Context Assembly
  ↓ LLM
  ↓ Answer + Citation

为什么

每一层都会影响最终质量：Chunk 太大影响定位，太小丢上下文；Embedding 影响语义召回；Metadata 决定权限与过滤；Retriever/Rerank 影响送给模型的证据质量。

实际项目怎么用

Spring AI 中可用 Document/Reader、EmbeddingModel、VectorStore、QuestionAnswerAdvisor 或 RetrievalAugmentationAdvisor 组织链路。企业项目应在 metadata 中保留 fileId、userId/tenantId、版本、来源等字段。

AI补充/纠错：原资料以 LangChain/Python 的 Loader、TextSplitter、Milvus 等举例；Java/Spring AI 不需要照搬类名。更重要的是职责边界。企业 RAG 还必须增加 ACL Filter、Hybrid Search、Rerank、Citation、增量索引和 Eval。尤其权限过滤应在 Retrieval 阶段执行，不能检索出无权限内容后再靠 Prompt 阻止模型泄露。

常见坑

固定字符数粗暴 Chunk；只调 Top-K；Embedding 模型升级却不重建向量；文档删除后旧 Chunk 仍残留；没有 ACL；没有离线检索评测与端到端 Eval。

面试口述版：RAG 的核心链路是文档加载、清洗分块、Embedding、VectorStore、Retriever、Context Assembly 和 LLM 生成。生产系统还要加入 Metadata/ACL、Hybrid Search、Rerank、Citation、增量更新和 Eval，因为最终效果往往由检索质量而不只是模型能力决定。

可能追问

RAG 效果差先换大模型吗？——通常先分层评估检索：正确 Chunk 有没有被召回、排名是否靠前、Context 是否完整，再判断生成模型问题。
