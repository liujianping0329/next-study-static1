先凭记忆回答，再展开答案。不要先看答案。

1. 本地缓存与 Redis 的根本取舍是什么？

本地缓存访问快、无网络开销，但每个实例各有一份数据，一致性困难；Redis 多实例共享，便于统一失效和跨实例访问，但增加网络与 Redis 可用性依赖。常见做法是 Caffeine L1 + Redis L2。

2. Cache-Aside 为什么常见“更新 DB → 删除 Cache”？

数据库作为事实源，写成功后删除旧缓存，让下一次读重新加载。相比同时更新 DB 和 Cache，删除能减少双写顺序、失败补偿和并发覆盖问题，但仍有短暂并发窗口，必要时结合 TTL、重试、消息/CDC 或版本控制。

3. 穿透、击穿、雪崩分别是什么？

穿透：大量请求查询根本不存在的数据；击穿：单个热点 Key 失效瞬间大量请求打 DB；雪崩：大量 Key 同时失效或缓存整体不可用导致后端被洪峰压垮。

4. 大量 MCP Server 为什么适合先选 Server 再选 Tool？

减少一次性暴露给模型的 Tool Schema 数量、Token 消耗和误选概率。先按领域/权限/租户路由到少量 Server，再在候选工具中做检索和调用。

5. 向量数据库在 RAG 哪一层？MMR/Rerank 做什么？

向量库主要负责 Retrieval 候选召回；MMR 在相关性与多样性之间平衡，Rerank 对候选做更精细的相关性排序。它们不是 Embedding 本身。

间隔复习：构造器循环依赖为什么三级缓存通常也解决不了？Kafka Consumer 超过 Partition 数量为什么不再增加并行度？

构造器参数必须在实例创建时就准备好，尚无可提前暴露的实例；Kafka 同一 Consumer Group 内一个 Partition 同一时刻只分配给一个 Consumer，多出的 Consumer 会空闲。

后端 #89｜Redis Hot Key：是什么、怎么发现

原资料出处：《后端高频面试题大集合》Redis / Hot Key 相关题。AI补充/纠错：具体阈值依业务容量、实例规格和延迟目标判断，不把某个固定 QPS 当统一标准。

白话理解

Redis 本来是用来替数据库扛流量的，但如果几十万请求都集中访问同一个 Key，压力就从数据库转移到了负责这个 Key 的 Redis 节点。Hot Key 的核心不是“数据大”，而是访问高度集中。

机制

大量请求
   ↓
user:hot-product:123
   ↓ hash / slot
Redis Cluster 某一个节点
   ↓
CPU / 网络 / 单 Key QPS 集中

Cluster 能把不同 Key 分散到不同 slot，但同一个 Key 的 slot 是固定的，因此简单扩容节点并不会自动把这个 Key 的请求拆散。

怎么发现

可从客户端 SDK/埋点统计 Key 访问频率，在网关或业务层按 Key 聚合，也可以结合 Redis 运行指标、slowlog、热点统计能力。大规模系统可把访问事件送入 Kafka，再用流式窗口统计 Top-N Key。

项目例子

秒杀商品详情 product:10086 平时 500 QPS，活动开始后突然 5 万 QPS。即使 Redis Cluster 有 10 个节点，这个 Key 仍主要命中其中一个节点。此时应先确认是不是单 Key 流量倾斜，而不是看到 Redis 慢就直接扩整个集群。

常见坑

把 BigKey 当 Hot Key；只看 Redis 总 QPS 不看 Key 分布；认为 Cluster 节点越多单 Hot Key 就自动均摊。

可能追问

Q：Hot Key 一定导致 Redis 宕机吗？
思路：不一定，取决于 QPS、Value 大小、网络、CPU 和命令复杂度，但它会造成局部瓶颈和负载倾斜。

Q：怎么在线发现？
思路：客户端采样 + Redis 指标 + 流式统计组合，避免为了统计本身制造过大开销。

Q：Hot Key 与 BigKey？
思路：前者是访问频率问题，后者是单值体积/元素规模问题。

30秒面试口述：Hot Key 是访问量高度集中在少数 Key，导致 Redis 某个节点 CPU、网络或吞吐成为瓶颈。Cluster 只能分散不同 Key，不能自动拆散同一个 Key。我会通过客户端采样、业务埋点和 Redis 指标发现热点，再用本地缓存、前置缓存或热点副本等方式分流。

一句话：Hot Key 不是东西大，而是找它的人太多。

后端 #90｜Redis Hot Key 怎么治理

原资料出处：《后端高频面试题大集合》Redis Hot Key 治理相关内容。AI补充/纠错：分布式锁主要解决“失效后并发重建”，不是持续命中型 Hot Key 的通用解法。

核心目标

不要让所有请求都走到同一个 Redis 节点。治理一般从“把请求挡在更前面”和“把同一热点拆成多份”两个方向做。

方案适合代价
Caffeine 本地缓存高频读、允许短暂不一致多实例失效同步
Gateway/Nginx 前置缓存公共热点内容缓存规则和失效治理
热点 Key 多副本读远多于写副本一致性、路由复杂度
预热 + 后台刷新可预测热点需要热点识别和刷新机制

两级缓存流程

Request
  ↓
Caffeine(L1) ──命中→ 返回
  ↓ miss
Redis(L2) ─────命中→ 回填 L1 → 返回
  ↓ miss
DB → Redis → L1 → 返回

更新数据时要考虑 L1 与 L2 的失效。可以通过消息广播让各实例删除本地缓存；即使消息偶尔失败，也用较短 TTL 做最终兜底。

为什么“加分布式锁”不等于治理 Hot Key

如果热点 Key 已存在且每次请求都命中 Redis，根本没有缓存重建竞争，锁不会减少读取 Redis 的次数。锁更适合热点 Key 过期瞬间的“缓存击穿”。

追问

本地缓存会不会脏？ 会，所以要明确一致性要求，用消息失效、版本号或短 TTL 控制窗口。
多副本怎么做？ 可把逻辑 Key 映射到多个物理副本并随机/哈希读取，但更新时必须处理副本失效。
什么数据不适合 L1？ 强一致、频繁写、敏感权限结果通常要谨慎。

30秒面试口述：治理 Hot Key 的核心是分流。我优先考虑 Caffeine L1 把热点挡在 JVM 内，再根据业务考虑前置缓存或 Redis 热点多副本。更新时通过消息或版本机制失效本地缓存并用 TTL 兜底。分布式锁主要处理失效后的并发重建，不是持续 Hot Key 的根本方案。

一句话：别让所有请求都走到同一个 Redis Key。

后端 #91｜Redis BigKey

原资料出处：《后端高频面试题大集合》Redis BigKey 相关题。AI补充/纠错：资料或网络常见的 KB、MB、集合元素数量只是经验阈值，BigKey 应结合延迟、网络、内存和运维影响判断。

白话理解

BigKey 是“一个 Key 背后的东西太重”。例如一个 String 存了数 MB JSON，或者一个 Hash/Set/List 塞了几十万元素。它与 Hot Key 可以独立存在，也可以同时发生。

为什么危险

Client → Redis
           ├─ 读取大 Value → 网络耗时/带宽
           ├─ 操作大集合 → 命令执行时间增长
           ├─ 删除大对象 → 内存释放成本
           └─ Cluster 迁移 → 单 Key 搬迁成本高

Redis 很多命令执行仍依赖主线程处理关键路径，因此一次重操作可能拖慢其他请求。

排查与治理

可以用 redis-cli --bigkeys 做抽样扫描，并用 MEMORY USAGE key 查看单 Key 内存占用。治理上拆分大 JSON、对集合分桶/分页、避免一次返回全部元素；删除很大的对象时可考虑 UNLINK，让内存回收异步处理。

Hot Key vs BigKey

Hot KeyBigKey
核心访问频率高Value/集合规模大
主要风险单节点流量倾斜网络、延迟、内存、迁移
典型治理分流/多级缓存拆 Key/分桶/分页

追问

DEL 和 UNLINK 区别？ UNLINK 将实际内存回收工作异步化，更适合大对象删除场景。
SCAN 安全吗？ 比 KEYS 更适合线上渐进遍历，但仍应控制频率和 COUNT。
大 Hash 怎么拆？ 可按业务维度或 hash 分桶，例如 user:profile:0..N。

30秒面试口述：BigKey 指单个 Value 很大或集合元素过多，会带来网络、主线程延迟、内存分布和 Cluster 迁移问题。我会通过 bigkeys、MEMORY USAGE 等定位，再按业务拆 Key、分桶或分页，删除大对象时考虑 UNLINK。

一句话：Hot Key 怕人多，BigKey 怕东西重。

Agent Tool Calling / MCP 1.1.10｜推理模型与 Tool Use / MCP

原资料出处：《AI应用开发面试题 / Agent / RAG》Tool Calling / MCP 专题。AI补充/纠错：MCP 是 Host/Client 与 Server 间的上下文与工具协议，不应把“某推理模型是否原生支持 MCP”与“宿主能否通过 MCP 调工具”混为一谈。

先拆层次

User
 ↓
Host / Agent Application
 ↓ 把可用工具 schema 提供给模型
LLM ──决定调用 tool X + arguments
 ↓
Tool Dispatcher / MCP Client
 ↓ MCP protocol
MCP Server
 ↓
真实 Java Service / DB / API
 ↓ tool result
LLM → 最终回答

模型真正做的是“根据工具描述决定要不要调用、调用哪个、参数是什么”。真正的网络连接、认证、权限、超时、重试和执行由 Host/Client/Server 侧完成。

与 Function Calling 的关系

Function/Tool Calling 更偏模型 API 层：模型输出结构化工具调用意图。MCP 更偏应用集成协议：统一发现和连接外部工具/资源。二者可以组合，而不是二选一。

Spring AI 视角

Java 应用可以把 Spring Service 方法包装成 Tool Callback；如果工具来自 MCP Server，则由 MCP Client 获取工具定义，再把候选工具提供给 ChatClient/模型。模型返回调用意图后，宿主执行并把结果送回模型。

为什么 Tool Schema 不是安全边界

Schema 能约束参数形状，但不能证明用户有权限执行操作。真实权限必须在服务端再次校验，例如 tenantId、userId、资源 ACL，不能相信模型生成的参数。

追问

MCP 等于 Agent 吗？ 不等于，MCP 是连接协议；Agent 还包含规划、循环、记忆、状态和终止条件。
模型不支持工具调用怎么办？ 可以由应用层做路由或结构化解析，但可靠性通常低于原生结构化 Tool Calling。
MCP Server 能直接信任模型吗？ 不能，认证、授权、参数校验、审计仍必须由系统执行。

30秒面试口述：我会把模型 Tool Calling 和 MCP 分层理解：模型负责根据 schema 选择工具并生成参数，Host 负责调度，MCP Client/Server 负责标准化连接真实工具。MCP 不是模型能力本身，所以不能简单说某推理模型“支持或不支持 MCP”；关键是模型的工具调用能力以及宿主的 MCP 集成。

一句话：模型负责选工具，Host/MCP 负责真正调用工具。

AI基础 #35｜大模型推理与检索系统性能优化

原资料出处：《AI大模型面试题-基础篇》性能优化相关题。AI补充/纠错：以下将通用 AI 性能优化转换为 Java / Spring AI / RAG 服务视角；具体优化项必须先通过指标确认瓶颈。

第一原则：先拆链路，再优化

HTTP Request
   ↓
Query Rewrite / Embedding
   ↓
Vector Retrieval
   ↓
Metadata ACL Filter
   ↓
Rerank
   ↓
Context Assembly
   ↓
LLM TTFT
   ↓
Token Generation
   ↓
Tool Call（如有）
   ↓
Response

如果总耗时 4 秒，必须先知道 4 秒花在哪里。Embedding 慢与 LLM 生成慢的解法完全不同。

常见优化

瓶颈手段注意
Embedding批处理、缓存、较小模型缓存要带模型/版本
RetrievalANN 参数、索引、过滤下推速度与 Recall 有取舍
Rerank减少候选、轻量 reranker别为了排序处理几百条
Context去重、压缩、Top-K 调整过度压缩会丢证据
LLM模型分级、流式输出、减少无效上下文TTFT 与总生成时间分开看
Tool并行独立调用、超时、连接池副作用工具不能随意并行/重试

为什么缓存不是万能答案

企业 RAG 的结果通常与知识版本、租户、用户 ACL、Prompt 版本、模型版本有关。如果只用 query 文本做缓存 Key，可能把 A 用户有权限看到的结果直接返回给 B 用户。因此缓存 Key 和失效策略必须包含必要的权限/版本维度。

Spring Boot 项目怎么量

给 Embedding、VectorStore、Rerank、ChatModel、Tool 分别打 timer/span，记录 P50/P95/P99、TTFT、输出 token 数、候选数量和错误率。先定位最长阶段，再做针对性优化。

追问

Top-K 越小越快，是不是越好？ 不是，太小会损失召回；需要离线评测 Recall/答案质量与延迟。
流式输出降低总耗时吗？ 不一定，它主要改善用户感知的首 Token 延迟。
RAG Cache 为什么必须考虑 ACL？ 因为相同问题对不同用户的可见文档集合可能不同。

30秒面试口述：AI 系统优化我不会先说加缓存，而是先把 Embedding、Retrieval、Rerank、Context、LLM TTFT/Generation 和 Tool Call 分段观测。确认瓶颈后再用缓存、批处理、ANN 参数、Top-K、上下文压缩、模型分级或并行 Tool 等手段。企业 RAG 的缓存还必须绑定知识版本和 ACL，避免越权。

一句话：先测哪段慢，再优化哪段。

Day 31 总结

今天三条主线：Redis 性能问题要先区分“访问倾斜”和“数据过大”；Agent 系统要分清模型 Tool Calling 与 MCP 的职责边界；AI 性能优化必须先把完整链路量化，再对症优化。
