复习来源：2026-09-13 正式 Day 14。先口述再展开答案；本次为自动执行，没有收到实时作答，因此不虚构掌握评分。

复习 1｜GC Roots

先回答：Java 为什么不怕普通循环引用？排查内存泄漏时为什么 Path to GC Roots 比单纯看“实例数最多”更重要？

答完后展开

Tracing GC 从 GC Roots 出发判断可达性。即使 A/B 相互引用，只要从任何 Root 都到不了它们，就仍然可回收。线上泄漏真正要找的是“谁把对象继续留住”，因此应查看到 GC Roots 的引用链和 retained size。

面试口述版：Java 主要使用可达性分析，不依赖引用计数，所以循环引用本身不是问题。发生 Heap 泄漏时我会通过 Path to GC Roots 找到具体引用链，而不是只看对象数量。

复习 2｜Mark-Sweep

先回答：标记-清除最大的结构性问题是什么？为什么它和“内存泄漏”不是同一个概念？

答完后展开

Mark-Sweep 回收后可能留下离散空闲区，形成外部碎片。碎片是空闲空间不连续；泄漏是本应释放的对象仍被引用，两者完全不同。

复习 3｜Mark-Copy

先回答：为什么年轻代特别适合复制思想？“复制算法一定浪费 50% 内存”为什么不够准确？

答完后展开

年轻对象通常死亡率高，因此只需移动少量存活对象，复制成本较低且回收后空间连续。50/50 是经典二等分模型，现代 Eden/Survivor 或 G1 Region evacuation 并不是简单永久浪费一半堆。

复习 4｜长期 Memory

先回答：ChatMemory、PostgreSQL 用户画像、VectorStore 长期语义记忆为什么要分层？

答完后展开

ChatMemory 适合最近会话；数据库适合可精确更新、删除、审计的偏好和事实；VectorStore 适合按语义召回历史摘要。三者职责不同，全部塞向量库会让精确事实更新和权限管理变得困难。

复习 5｜依赖管理

先回答：Java/Spring AI 项目里，为什么 BOM + Wrapper + 固定 JDK + CI clean build 比“大家装同一个 Maven”更可靠？

答完后展开

BOM 管兼容版本，Wrapper 固定构建工具版本，固定 JDK 避免语言/运行时差异，CI clean build 验证项目在干净环境能复现。目标是可重复、可测试、可回滚，而不是依赖某台开发机。

间隔复习｜约 3 天前：Class Identity

为什么可能出现 com.demo.User cannot be cast to com.demo.User？

答完后展开

JVM 的类身份由二进制类名和 defining ClassLoader 共同决定。两个不同 ClassLoader 分别定义同名类时，它们就是不同类型。

间隔复习｜约 7 天前：线程池

为什么一个非常大的队列会让 maximumPoolSize 很难发挥作用？

答完后展开

ThreadPoolExecutor 在 core 满后优先入队，只有队列满了才继续扩到 maximumPoolSize。超大队列会让请求长期排队，最大线程数一直触发不到，尾延迟可能持续恶化。

② 新题 1｜Mark-Compact 标记-整理算法原理和优缺点

原资料：《后端高频面试题大集合》JVM 第 15 题“介绍下JVM的标记-整理算法原理和优缺点”｜PDF 第 56～57 页。正式后端 #41。

概念

Mark-Compact（标记-整理 / 标记-压缩）可以理解成：

Mark：找出存活对象
  ↓
Compact：把存活对象向一端移动
  ↓
清理边界外空间

示意：

整理前：[A活][垃圾][B活][空][C活][垃圾]

移动后：[A活][B活][C活][连续空闲........]

原理

它与 Mark-Sweep 的关键区别是会移动存活对象。正因为做了压缩，回收后可以获得连续空间，显著降低外部碎片。

为什么

在存活率高的区域，如果使用纯复制算法，需要搬运大量对象并准备额外目标空间；如果只做 Mark-Sweep，又可能留下大量碎片。因此“标记后压缩”适合解释传统老年代的回收思路。

实际项目怎么用

面试和 GC 日志分析时，可以把三种基础算法放一起比较：

算法主要优势主要代价典型理解
Mark-Sweep不必搬所有存活对象碎片基础非移动回收思想
Mark-Copy回收后连续、低存活率快额外空间 + 搬运年轻代 / evacuation 思想
Mark-Compact连续空间、无典型外部碎片移动和引用更新成本高存活率区域的压缩思想

AI补充/纠错

AI补充/纠错：原资料把 Mark-Compact 直接说成“老年代回收算法”适合教学，但现代 G1、ZGC 等收集器不能简单套成“老年代 = Mark-Compact”。今天更稳的说法是：Mark-Compact 是基础算法思想，适合解释高存活率区域为什么需要压缩；现代收集器会结合 Region、并发标记、evacuation、barrier 等机制实现更复杂的回收。

常见坑

  • 把 Mark-Compact 和 Mark-Sweep 混成同一个算法。
  • 只说“没有碎片”，不提对象移动和引用更新成本。
  • 把基础算法直接等同于某个现代 GC 的完整实现。
面试口述版：Mark-Compact 先从 GC Roots 标记存活对象，再把存活对象向一端移动，最后清理边界外的垃圾。相比 Mark-Sweep，它解决了外部碎片；相比经典 Copying，又不需要永久准备同等大小的完整空间。代价是对象移动和引用更新成本，因此更适合解释存活率较高区域的回收思想。

可能追问

对象移动后引用如何更新？为什么压缩能改善大对象分配？G1 evacuation 与 Mark-Compact 有什么异同？

③ 新题 2｜JVM 分代收集思想到底解决什么问题？

原资料：《后端高频面试题大集合》JVM 第 16 题“说下JVM垃圾回收的分代收集算法思想”｜PDF 第 58～59 页。正式后端 #42。

概念

分代的核心不是“必须有 Eden、S0、S1”，而是基于对象生命周期差异：

大多数对象：创建后很快死亡
少量对象：长时间存活

→ 对不同年龄/区域采用不同回收策略

原理

经典 HotSpot 教学模型：

Young
├─ Eden
├─ Survivor 0
└─ Survivor 1

Old
└─ 长寿命对象

年轻代死亡率高，适合高频回收与复制/转移思路；老年代存活率高，回收频率低，对压缩、并发和暂停控制要求更高。

为什么

如果整个堆每次都采用完全相同的扫描和搬运策略，会浪费大量工作。分代假说让 GC 把更多精力放在最可能产生垃圾的区域，提高总体效率。

实际项目怎么用

线上调优不要只背年轻代比例，而应观察：

Allocation Rate
Young GC frequency
Young GC pause
Promotion rate
Old occupancy
Concurrent cycle
Full GC / allocation failure

例如大量短命 DTO、JSON、临时集合会提高 allocation rate；如果 Survivor / 回收节奏不合适，可能造成过早晋升，增加老年代压力。

AI补充/纠错

AI补充/纠错：原资料“老年代满就会触发 Full GC”过于绝对。现代 G1 会通过并发标记和 mixed collection 等机制尽量在真正耗尽前回收老年代 Region；不同收集器对 Major/Full GC 的定义与触发条件也不同。另一个重点是：分代思想与“固定连续 Young/Old 物理布局”不是同一个概念，G1 同样体现分代，但底层是 Region 化管理。

常见坑

  • 把分代收集等同于固定 8:1:1。
  • 认为所有对象都严格“Eden → Survivor → Old”按固定次数移动。
  • 看到 Young GC 多就直接判定有问题；高 allocation 场景本来就可能频繁 Young GC。
面试口述版：分代收集基于一个重要假设：绝大多数对象生命周期很短，少量对象会长期存活。因此 JVM 可以对年轻对象高频快速回收，对长期存活对象采用更适合高存活率的策略，从而减少每次都处理整堆的成本。现代 G1 虽然使用 Region，也仍然体现年轻代和老年代的分代思想。

什么是晋升？什么是过早晋升？G1 为什么既 Region 化又仍然算分代 GC？

④ 新题 3｜Partial GC、Full GC 与 STW 的关系

原资料：《后端高频面试题大集合》JVM 第 17 题“介绍下JVM垃圾回收里面的Partial GC/Full GC/STW概念”｜PDF 第 59～60 页。正式后端 #43。

概念

术语更稳的理解
Partial GC只回收 Java Heap 的一部分区域；Young GC 属于典型 Partial GC。
Major / Old GC通常指老年代相关回收，但术语在不同收集器和资料里并不完全统一。
Full GC范围更广、成本通常更高的全堆/全局性回收事件；具体行为取决于收集器。
STWStop-The-World：应用线程在某个 GC 阶段被暂停。

原理

STW 是“暂停行为”，不是某一种 GC 类型：

Young GC  ─┐
Mixed GC  ─┼→ 某些阶段可能 STW
Full GC   ─┘

STW ≠ Full GC 的同义词

即使是并发收集器，也通常仍有需要 Stop-The-World 的阶段，只是努力把重工作并发化、缩短暂停。

为什么

GC 需要在某些阶段获得稳定的对象图或完成引用更新。如果用户线程同时无限制修改引用关系，就很难保证正确性，所以会借助 safepoint、barrier、并发标记协议等机制协调。

实际项目怎么用

线上卡顿不要只看“有没有 Full GC”，而应直接看：

GC pause duration
pause frequency
GC cause
Young / Mixed / Full
allocation failure
concurrent cycle duration
p95 / p99 application latency

一次 80ms Young GC 可能比一次低频 Full GC 更影响某些实时接口；反过来，频繁 Full GC 往往又意味着更严重的容量或引用问题。

AI补充/纠错

AI补充/纠错：原资料“Minor GC、Major GC 都会 STW，区别只在时间长短”过度简化。现代收集器包含并发阶段和暂停阶段，不能只靠 Minor/Major 名字判断停顿模型。原资料还写“Major GC 通常比 Minor GC 慢 10 倍以上”，这种固定倍数不应背诵；真实暂停取决于收集器、堆大小、存活对象量、硬件和配置。另：System.gc() 通常只是显式 GC 请求，不保证一定以某种固定 Full GC 方式执行。

常见坑

  • 把 STW = Full GC。
  • 把 Major GC 和 Full GC 在所有 JVM/GC 上强行定义成完全一样。
  • 只看 GC 次数，不看 pause、cause 和业务延迟。
面试口述版：Partial GC 表示只回收堆的一部分，例如 Young GC；Full GC 通常表示范围更广、代价更高的全局回收，但不同收集器细节不同。STW 则是应用线程暂停这一行为，不等于 Full GC。现代并发收集器也会有短暂 STW 阶段，所以生产排查我重点看具体 pause、GC cause 和 p95/p99，而不是只背 Minor、Major、Full 的名字。

⑤ 新题 4｜Cursor 的“记忆”机制应该怎么理解？

原资料：《AI应用开发面试题 / Agent / RAG》1.1.15“对 Cursor 记忆管理机制的了解”｜PDF 第 28～29 页。

概念

Cursor 这类 Coding Agent 的“记忆”不能只理解成一个 Vector DB。至少可以拆成：

项目规则 / User Rules
+ 当前对话上下文
+ 代码库检索上下文
+ 项目文件中的显式知识
+ 外部 MCP / 自建 Memory（可选）

原资料内容

原资料把 Cursor Rules、内置 Memories、社区 Memory Bank、MCP Memory Server 分成几层。核心思想是正确的：稳定规则、项目事实、会话状态、语义历史并不应该混成一种存储。

当前机制与版本纠错

AI补充/纠错（2026-09）：Cursor 官方当前明确支持 Project Rules、User Rules、Team Rules 和 AGENTS.md。Project Rules 放在 .cursor/rules，使用 .mdc 文件并可按 always/relevance/path/manual 等方式作用；Rules 本质上是在模型上下文中持续注入可复用指令。原资料把 Memory Bank、Basic Memory 等社区方案和 Cursor 官方原生能力放在同一层容易让人误以为它们都是 Cursor 官方 Memory API，面试时应明确区分“官方 Rules/上下文能力”和“社区/外部记忆方案”。

为什么

编码 Agent 最大的问题之一是跨会话一致性：

项目约定
编码规范
架构边界
禁止操作
当前进度
历史决策

如果每次都靠人重新描述，成本高且容易漂移；但如果把所有历史自动永久化，又会产生过期规则、冲突记忆和 Token 膨胀。

实际项目怎么用｜映射到你自己的 Agent

Cursor 思路Spring Boot / Spring AI 可以怎么做
Project Rules版本控制的 system instructions / 项目 policy 文件
User Rulesuser_profile / preference 表
最近会话ChatMemory
代码库上下文RAG / Repo Search / Tool
历史决策结构化 DB + VectorStore 混合

常见坑

  • 把 Rules 当成模型真的“学会并写进权重”。它只是持久化上下文/指令。
  • 把社区 Memory Bank 说成 Cursor 官方强制机制。
  • 规则文件越写越大，导致 Token 浪费和指令冲突。
  • 把敏感账号信息、密钥写进 Rule / Memory。
面试口述版：Cursor 的长期一致性主要依赖规则和项目上下文，而不是模型自己永久记住。官方现在有 Project Rules、User Rules、Team Rules 和 AGENTS.md；Project Rules 可以版本控制并按范围注入模型上下文。社区还可以通过 Memory Bank 或 MCP 接外部记忆，但我会把它们与 Cursor 官方机制区分开。自己做 Coding Agent 时也会把稳定规则、用户偏好、短期 ChatMemory 和代码 RAG 分层管理。

⑥ 新题 5｜Prompts / 提示工程模块是什么？Spring AI 怎么实现？

原资料：《AI大模型面试题-基础篇》第 17 题“LangChain中的Prompts（提示工程）模块是什么？如何有效使用？”｜PDF 第 13～14 页。原 PDF #15 后直接进入 #17，因此 #16 继续保留缺号。

概念

Prompt 工程不只是“写一句更聪明的话”，而是把模型输入设计成稳定、结构化、可复用、可测试的接口。

System Instructions
+ User Input
+ Variables
+ Retrieved Context
+ Tool Information
+ Output Contract
= Prompt

原理

原资料把 Prompt Template 类比传统模板引擎，这个类比很好理解：

固定模板：
请根据 {document} 回答 {question}

运行时：
document = 检索到的内容
question = 用户问题

→ 渲染成最终 Prompt

Spring AI 当前也提供 Prompt、PromptTemplate、System/User Message 以及 ChatClient 模板变量。

Java / Spring AI 实际项目怎么用

String answer = chatClient.prompt()
    .system("你是企业数据助手，只能根据授权数据回答")
    .user(u -> u
        .text("请解释 {term}，并给出 Java 示例")
        .param("term", term))
    .call()
    .content();

或者底层使用：

PromptTemplate template = new PromptTemplate(
    "请用 {language} 解释 {topic}"
);
Prompt prompt = template.create(Map.of(
    "language", "中文",
    "topic", "JVM GC"
));

为什么

模板化的价值主要是工程治理：

  • 把稳定指令和动态用户输入分开。
  • 减少字符串手工拼接。
  • 同一 Prompt 可以版本管理与回归测试。
  • 更容易统一输出格式、安全约束和业务边界。

AI补充/纠错

AI补充/纠错：原资料强调“模板写得清晰”没有问题，但现代 AI 应用不能把所有系统能力都塞进 Prompt。权限校验、SQL 白名单、Tool 授权、数据过滤必须由程序代码强制执行，不能只写一句“禁止访问未授权数据”。另外不要要求模型向终端用户输出完整私有 Chain-of-Thought；更适合要求给出简洁结论、关键依据和可验证的结果。Spring AI 2.0.1 的 ChatClient 本身支持 user/system 模板变量，底层则使用 PromptTemplate / TemplateRenderer。

常见坑

  • 直接字符串拼接用户输入，导致 Prompt Injection 风险扩大。
  • Prompt 里说“只能 SELECT”，代码却真的允许执行 UPDATE/DELETE。
  • 模板塞入无限 RAG 文档，Token 成本和注意力反而恶化。
  • Prompt 改动没有版本、测试集和回归评估。
面试口述版：Prompt 模块的作用是把系统指令、用户输入和动态变量结构化地组织起来，使提示词可复用、可维护、可测试。Spring AI 可以通过 ChatClient 的 system/user 模板或 PromptTemplate 实现变量渲染。我会把 Prompt 当成业务接口的一部分做版本管理和评测，但安全权限仍由 Java 代码强制保证，不能依赖模型自觉遵守。
