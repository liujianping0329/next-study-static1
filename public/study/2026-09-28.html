② 新题 1｜BeanDefinition 是什么？

《后端高频面试题大集合》Spring #7｜正式后端 #83

概念→原理→为什么

BeanDefinition 是 Spring 对 Bean 创建与管理方式的元数据抽象，描述 class、scope、lazy、依赖和初始化方法等。配置先解析成 BeanDefinition，再由容器创建 Bean。

XML / Annotation / @Bean → BeanDefinition → Registry → BeanFactory → Bean

实际项目怎么用

Starter、动态注册和框架扩展常接触 BeanDefinitionRegistry、ImportBeanDefinitionRegistrar。

AI补充/纠错：BeanDefinition 是配置元数据，不是最终业务 Bean 实例。

常见坑→面试怎么说→可能追问

Spring 先把不同配置来源统一成 BeanDefinition，再由 BeanFactory 创建管理 Bean。追问：BeanDefinitionRegistryPostProcessor 与 BeanFactoryPostProcessor 区别？

② 新题 2｜Spring Bean 生命周期

《后端高频面试题大集合》Spring #8｜正式后端 #84
实例化 → 属性注入 → Aware → BeanPostProcessor before → 初始化 → BeanPostProcessor after → 可用 Bean → 销毁

实际项目怎么用

生命周期能解释 AOP 代理、资源初始化与容器扩展。初始化常见 @PostConstruct / InitializingBean / init-method；销毁常见 @PreDestroy / DisposableBean / destroy-method。

AI补充/纠错：实例化和初始化不是同一步。AOP 自动代理通常也通过 BeanPostProcessor 体系参与，后置处理返回的对象可能已经是代理。

面试怎么说→可能追问

先实例化、注入，再执行 Aware、前置处理、初始化和后置处理，关闭容器时执行销毁回调。追问：BeanFactoryPostProcessor 和 BeanPostProcessor 分别处理什么？

② 新题 3｜Spring 循环依赖与三级缓存

《后端高频面试题大集合》Spring #9｜正式后端 #85
singletonObjects → 完整单例
earlySingletonObjects → 早期引用
singletonFactories → ObjectFactory

典型 singleton 属性注入循环依赖通过提前暴露引用解决：A 实例化后暴露 ObjectFactory，创建 B 时需要 A，可取得 A 的早期引用，随后完成 B 和 A。

AI补充/纠错：原资料“不推荐构造器注入”不适合作为现代 Spring 建议。应优先构造器注入，它能显式暴露必需依赖和循环设计问题。构造器循环依赖不能靠典型三级缓存解决，prototype 循环依赖也不能这样解决。

实际项目→常见坑→面试怎么说→追问

业务设计应优先消除循环依赖。三级缓存的重要意义之一是通过 ObjectFactory 为早期代理引用留下处理空间。追问：为什么两级缓存不够？

② 新题 4｜1000 个 Tools 怎么工作？

《AI应用开发面试题 / Agent / RAG》Tool Calling / MCP 1.1.8

全量注入 1000 个 Schema 会造成 Token 膨胀、误选和延迟。原资料给出两阶段路由、语义检索 Top-K、分层注册、描述压缩与动态加载。

请求 → 领域过滤 → Tool Retrieval → Top-K → LLM 精选 → 执行

Spring Boot / Spring AI 项目

Java 层维护 Tool Registry，先按 domain、tenant 等条件缩小范围，再用 Embedding/Reranker 选候选，最后只给本轮 ChatClient 暴露少量 Tool。

AI补充/纠错：Tool Retrieval 不能只看向量相似度；Tool Schema 更新后也要同步刷新检索索引。

面试怎么说→追问

先路由/检索缩小候选，再动态注入 Top-K；核心工具常驻、长尾按需加载。追问：路由选错怎么办？可 fallback、二次检索、低置信度拒绝与 Eval。

② 新题 5｜MMR 检索

《AI大模型面试题-基础篇》#33｜Maximal Marginal Relevance

MMR 同时考虑 Query 相关性和已选结果间的重复度，用 λ 平衡相关性与多样性。

score(d)=λ·Sim(query,d)-(1-λ)·max Sim(d,selected)
λ 大 → 偏相关；λ 小 → 偏多样

为什么→实际项目怎么用

普通 Top-K 可能返回大量近似 Chunk；MMR 能在保持相关的前提下覆盖更多角度，例如数据库优化同时召回索引、SQL、分区等内容。

AI补充/纠错：MMR 的直接目标是减少冗余并平衡相关性/多样性，不应把“提高 Recall”理解成必然提升传统 Recall 指标。λ、候选池和最终 Top-K 应通过 RAG Eval 调参。

常见坑→面试怎么说→可能追问

不是越多样越好，λ 太低会损失相关性。面试：纯相似度只看 Query-Document，MMR 还惩罚已选结果之间的重复。追问：MMR 与 Cross-Encoder Reranker 可以组合吗？可以，二者解决的问题不同。
