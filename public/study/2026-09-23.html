复习 1｜DLX

RabbitMQ 的 DLX 与“死信队列”是什么关系？DLX 本身负责长期存储消息吗？

答完后展开

DLX 是 Exchange，负责把死信重新路由；所谓死信队列通常是绑定到 DLX、真正接收死信的 Queue。

面试口述版：DLX 是死信重新发布后的路由入口，不是存储本体；目标 Queue 才承载死信，后续还要配监控、重试上限和补偿。

复习 2｜死信条件

哪些情况会产生死信？为什么 unroutable message 不应该简单算作 Queue 内死信？

答完后展开

典型条件包括 reject/nack 且 requeue=false、TTL 过期、Queue 超限、Quorum Queue 超过 delivery-limit。Unroutable message 可能根本没有进入 Queue，属于发布路由失败，应从 mandatory/return 等发布链路处理。

复习 3｜KRaft

KRaft 相比 ZooKeeper 架构解决了什么问题？Controller Quorum 负责什么？

答完后展开

KRaft 把 Kafka 元数据管理收回 Kafka 自身，由 Controller Quorum 维护元数据日志与集群控制状态，减少外部 ZooKeeper 依赖并统一一致性模型。

复习 4｜Tool Calling

Tool Schema 为什么既影响模型选工具，也可能成为安全风险？

答完后展开

Schema 的 name/description/parameters 帮助模型选择和构造参数，但模型生成合法参数不等于有业务权限。真正执行前仍要在 Java 层做白名单、ACL、参数校验、幂等和危险操作确认。

复习 5｜RAG

为什么 RAG 不等于“VectorStore + Top-K”？

答完后展开

生产 RAG 还包括解析、Chunk、Embedding、Metadata、权限过滤、Hybrid Search、Rerank、Context Assembly、Citation 与 Eval；检索质量和权限边界都会影响最终结果。

间隔复习｜约 3 天前

RabbitMQ Quorum Queue 为什么比旧 Classic Mirrored Queue 更适合作为现代高可用方案？

答完后展开

Quorum Queue 基于多数派复制与一致性机制设计，旧 Classic Mirrored Queue 已退出现代 RabbitMQ 主线。高可用仍需合理节点数、故障域与客户端重连设计。

间隔复习｜约 7 天前

JVM CPU 高时为什么要连续采样线程栈，而不是只抓一次 jstack？

答完后展开

单次快照可能只捕获瞬时状态；连续采样才能判断同一线程是否持续占用 CPU，并区分业务热点、锁竞争、GC 或偶发尖峰。

② 新题 1｜Kafka 有哪些核心概念？

原资料：《后端高频面试题大集合》MQ 第17题｜PDF 第95～96页。正式后端 #68。

概念

概念作用
BrokerKafka 服务节点，承载分区副本
Producer向 Topic 生产 Record
Topic消息逻辑分类
PartitionTopic 的并行与有序基本单元
ReplicaPartition 的数据副本
Leader / FollowerLeader 对外处理读写，Follower 复制
Consumer Group共同消费 Topic 的消费者集合
Offset消费者在 Partition 上的消费位置

原理 → 为什么

Topic
├─ Partition 0 → Leader + Followers
├─ Partition 1 → Leader + Followers
└─ Partition 2 → Leader + Followers

Consumer Group A
├─ Consumer 1 ← P0,P1
└─ Consumer 2 ← P2

Partition 同时承担并行度、局部顺序和数据分布三个职责，所以 Kafka 的吞吐扩展不是单纯“多加 Consumer”。

实际项目怎么用

订单事件可按 orderId 作为 Key，让同一订单尽量落在同一 Partition，从而保持该 Key 的分区内顺序；不同 Consumer Group 可以分别做通知、分析、风控。

AI补充/纠错：原资料写“offset 保存在消费端消费者组里”不够准确。现代 Kafka 的 group offset 通常提交到 Kafka 内部主题，由 Group Coordinator 管理。另一个重点是：Kafka 保证的是 Partition 内顺序，不是整个 Topic 的全局顺序。

常见坑

把 Topic 当 Queue；认为一个 Group 内每个 Consumer 都能收到同一条消息；认为 Consumer 数量超过 Partition 后还能线性提升吞吐。

面试口述版：Kafka 的核心是 Topic、Partition、Replica、Broker、Producer、Consumer Group 和 Offset。Partition 是并行和有序的基本单元，一个 Group 内同一 Partition 同一时刻只分配给一个 Consumer，因此有效并行度受 Partition 数限制。

可能追问

为什么 Partition 数不能无限加？——它会增加元数据、文件句柄、复制、Leader Election 与 Rebalance 等成本。

② 新题 2｜Consumer Group 如何实现负载均衡与水平扩展？

原资料：《后端高频面试题大集合》MQ 第18题｜PDF 第96～97页。正式后端 #69。

概念

同一个 Consumer Group 中，Topic 的每个 Partition 在一个时刻只分配给组内一个 Consumer；多个不同 Group 则可以各自独立消费同一 Topic。

原理

Topic: 6 Partitions
Group A:
C1 → P0,P1
C2 → P2,P3
C3 → P4,P5

再加 C4 → 触发重新分配
如果 Consumer > Partition → 部分 Consumer 空闲

Consumer 加入、离开，或 Partition 数变化时，需要重新协调分区归属，这就是 Rebalance 相关问题。

为什么

Partition 把一个 Topic 拆成可并行消费的单元，Consumer Group 再把这些单元分配给多个实例，从而获得水平扩展能力。

实际项目怎么用

Spring Kafka 服务扩容前先检查 Partition 数。如果 Topic 只有 3 个 Partition，把同一 Group 扩到 10 个实例并不会得到 10 倍消费并行度。

AI补充/纠错：“增加 Consumer 就能提升吞吐”有前提：必须有足够 Partition，而且下游 DB/API、CPU、网络没有成为新瓶颈。频繁扩缩容还会带来 Rebalance 成本；现代客户端应关注 cooperative/incremental rebalance 等减少停顿的策略。

常见坑

Consumer 数远大于 Partition；把不同业务放进同一 Group 导致消息被竞争消费；忽略 Rebalance 期间延迟；处理时间过长导致消费者被判定异常。

面试口述版：Kafka 通过 Consumer Group 将 Partition 分配给组内 Consumer，实现负载均衡。扩 Consumer 的上限受 Partition 数约束，成员变化会触发重新协调，因此生产上要同时规划 Partition、消费实例数和 Rebalance 成本。

可能追问

广播怎么做？——让不同业务使用不同 Consumer Group；每个 Group 都能独立看到 Topic 的消息流。

② 新题 3｜Kafka Producer 的发送过程

原资料：《后端高频面试题大集合》MQ 第19题｜PDF 第97～98页。正式后端 #70。

概念 → 原理

ProducerRecord
  ↓ serialize
  ↓ partition
RecordAccumulator / Batch
  ↓ Sender
Partition Leader Broker
  ↓ replica replication
ACK / error / retry

Producer 并不是每条消息都立即单独发网络请求，而是通过客户端缓冲和 Batch 提高吞吐；目标 Partition 的 Leader 负责接收写入。

为什么

Batch 能减少系统调用和网络请求次数，配合压缩可显著提高吞吐；Key 则常用于稳定地把相关业务事件映射到同一 Partition。

实际项目怎么用

订单事件用 orderId 做 Key；通过 acks、retries、delivery.timeout、batch.size、linger.ms、compression 等参数在可靠性、延迟和吞吐之间取舍。

AI补充/纠错：原资料写“无 Key 默认 RoundRobin”属于旧式简化。现代 Kafka Producer 的默认分区策略对无 Key 记录会采用 sticky/自适应批处理思路，而不是机械地每条消息 round-robin；不要把旧实现细节当永久规则。另一个纠错：资料中的“默认缓冲区 16KB”混淆了 batch.size 与总 buffer.memory，它们不是同一个参数。

常见坑

只看 send() 没处理异步失败；Key 设计导致热点 Partition；盲目增大 Batch 导致延迟/内存上升；认为 Producer ACK 就等于下游业务消费完成。

面试口述版：Kafka Producer 会先序列化并选择 Partition，把 Record 放入客户端 Accumulator 形成 Batch，由 Sender 发给该 Partition Leader，再根据 acks 等配置等待 Broker 确认。Key 常用于分区稳定性和局部顺序，Batch/压缩则主要优化吞吐。

可能追问

如何避免重复写？——结合 idempotent producer、合理的 acks/retry 配置；跨多个 Partition 的原子写则进一步考虑 Kafka Transaction。

② 新题 4｜MCP 和 Function Calling 有什么区别？

原资料：《AI应用开发面试题 / Agent / RAG》Tool Calling 专题 1.1.3｜PDF 第41页。

概念

Function Calling / Tool Calling 是模型根据 Tool Schema 生成结构化调用意图的能力；MCP（Model Context Protocol）则标准化 Host/Client 与外部 Server 之间如何发现和使用工具、资源、Prompt 等能力。

原理

LLM
 ↓ tool decision
Host / Agent Application
 ↓ MCP Client
MCP Server
 ├─ Tools
 ├─ Resources
 └─ Prompts
 ↓
External System

两者不是竞争关系：Tool Calling 解决模型“决定调用什么并生成参数”，MCP 解决外部能力如何用统一协议暴露、发现和连接。

实际项目怎么用

Spring AI 应用内部少量固定业务函数可以直接使用 @Tool；如果希望 GitHub、数据库、文件系统等能力被多个 AI Host 复用，则 MCP 更适合作为标准化集成边界。

AI补充/纠错：原资料把 MCP 概括成 Tools / Resources / Prompts / Sampling 四类能力适合作为历史理解，但协议正在演进。2026-07-28 现代协议已经对 Sampling、Roots、Logging 等能力做弃用/生命周期调整，因此面试不要把某一版能力清单说成永远不变。核心不变的是：MCP 是模型上下文与外部能力集成协议，不等于模型自身的 Function Calling。

常见坑

认为用了 MCP 就不需要 Tool Calling；把 MCP Server 当 LLM；把所有工具全部注入导致 Token 与选错工具概率上升；没有做 MCP Server 身份、授权和危险操作确认。

面试口述版：Function Calling 是模型层面的工具调用能力，MCP 是应用与外部工具/数据源之间的标准化协议。模型仍然负责决定是否调用工具，MCP 负责让工具以统一方式被发现、连接和执行。Java 项目可以用 MCP Java SDK/Spring AI MCP 集成外部 Server，同时在业务层继续做权限和审计。

可能追问

MCP 一定走网络吗？——不一定，本地集成可以走 stdio，远程场景通常使用 Streamable HTTP 等标准传输。

② 新题 5｜RAG 相比纯大模型有什么优势？

原资料：《AI大模型面试题-基础篇》RAG 第28题｜PDF 第23～24页。

概念

RAG 在生成前检索外部知识，把相关证据与用户问题一起提供给模型，使回答不必完全依赖模型训练时写入参数的知识。

为什么

优势原因
时效性知识库可独立更新，无需重新训练模型
降低幻觉风险生成阶段获得外部证据
可追溯可记录并展示来源 Chunk / 文档
私有知识可检索企业内部数据
维护成本知识更新通常比重新 Fine-tune 更轻

实际项目怎么用

企业制度、技术手册、客服政策、经常更新的产品知识都适合 RAG；在 Spring AI 中可以用 Document → Chunk → EmbeddingModel → VectorStore → Retriever/Advisor → ChatClient 形成链路。

AI补充/纠错：RAG 只能“降低”幻觉，不能保证正确；它也不是所有问题都适合。稳定的行为风格/格式学习可能更适合 Prompt 或 Fine-tuning；实时精确数值更适合 Tool/API；权限敏感企业知识必须在 Retrieval 阶段做 ACL/Metadata Filter。

常见坑

只做向量 Top-K；Chunk 过大/过小；Embedding 与业务语言不匹配；不做 Rerank；不记录 Citation；把无权限文档先检索出来再靠 Prompt 禁止回答。

面试口述版：RAG 的优势是让模型在回答前动态获取外部知识，因此知识更新快、可接企业私有数据、能提供来源并降低幻觉风险，而且更新知识通常无需重新训练模型。但最终质量取决于检索、权限、Chunk、Rerank 和 Context Assembly，RAG 不是正确率保证器。

可能追问

RAG 与 Fine-tuning 怎么选？——需要动态事实和可引用知识优先 RAG；需要改变模型行为、风格或特定任务能力时再考虑 Fine-tuning，也可以组合使用。
