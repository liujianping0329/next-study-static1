复习 1｜VHost

RabbitMQ VHost 能隔离哪些东西？为什么它不能当成物理资源隔离？

答完后展开

VHost 隔离 Exchange、Queue、Binding、权限等逻辑资源，但同一 Broker 的 CPU、内存、磁盘、网络仍然共享。

面试口述版：VHost 是 RabbitMQ 的逻辑命名空间和权限边界，不是独立 Broker，不能解决底层资源争抢。

复习 2｜顺序消息

为什么“单 Queue = 业务绝对有序”不成立？

答完后展开

多 Consumer、并发 Publisher、重试/requeue、优先级都可能影响最终处理顺序。生产系统通常按业务 Key 路由，并配合幂等、状态机和版本号。

复习 3｜Exchange

Direct、Fanout、Topic、Headers 的路由差异是什么？Exchange 自己负责持久保存消息吗？

答完后展开

Direct 精确匹配 Routing Key；Fanout 广播；Topic 模式匹配；Headers 按 Header 匹配。Exchange 核心职责是路由，消息可靠保存主要由 Queue 等机制承担。

复习 4｜Tool Calling

LLM 生成 tool_call 后，真正执行数据库/API 的是谁？为什么危险操作不能只靠 Prompt 限制？

答完后展开

真正执行的是应用层代码。LLM 的 tool_call 只是结构化调用请求；权限、参数校验、幂等、事务、危险操作确认必须由 Java 应用强制执行。

复习 5｜幻觉

为什么 RAG 和 temperature=0 都不能保证完全没有幻觉？

答完后展开

RAG 可能检索错、证据可能过期，模型也可能脱离证据扩写；降低 temperature 只减少随机性，不等于事实校验。

间隔复习｜约 3 天前

RabbitMQ Publisher Confirm 成功是否代表消费者业务事务已经成功？

答完后展开

不是。Confirm 覆盖 Publisher 到 Broker；Consumer 端仍需要 ACK、业务事务、幂等、重试和补偿。

间隔复习｜约 7 天前

G1 为什么叫 Garbage-First？

答完后展开

G1 将堆划分为 Region，并根据存活量、回收收益与暂停预算选择更值得回收的 Region，而不是每次固定处理整个老年代。

② 新题 1｜RabbitMQ 死信队列和业务场景

原资料：《后端高频面试题大集合》MQ 第14题｜PDF 第91～92页。正式后端 #65。

概念

RabbitMQ 中真正的概念是 Dead Letter Exchange（DLX）：消息在源 Queue 中成为死信后，会被重新发布到配置的 DLX，再根据 Binding 路由到目标 Queue。所谓“死信队列”通常是接收这些死信的目标 Queue。

原理 → 为什么

Producer → Exchange → Source Queue
                       │ TTL / reject / limit
                       ↓
                      DLX
                       ↓
                Dead-letter Queue
                       ↓
             补偿 / 人工处理 / 延迟任务

它把无法正常处理或需要延迟处理的消息从主消费链路分离，避免异常消息持续阻塞正常业务。

实际项目怎么用

订单超时关闭、Push 延迟触发、消费失败隔离、人工补偿。延迟任务常见做法是 TTL + DLX，但需要理解 TTL 消息的实际过期/投递行为。

AI补充/纠错：原资料写“RabbitMQ 本身不支持延迟队列，只能靠死信实现”属于简化表述。DLX+TTL 是经典方案，但生产上还要考虑插件/调度系统等方案。更重要的是：DLX 重新发布本身也可能失败；Quorum Queue 可选择 at-least-once dead-lettering，通过内部 Publisher Confirm 提高死信转移可靠性，但默认仍是 at-most-once。

常见坑

把 DLX 当存储；死信队列无限增长；死信再次失败形成循环；把“进入 DLQ”当成问题已经解决。

面试口述版：RabbitMQ 的 DLX 用于接收源 Queue 中被拒绝、过期或超限等死信，再路由到专门 Queue。业务上常用于失败隔离、补偿和延迟处理；DLQ 不是终点，还需要监控、重试上限和人工/自动补偿。

可能追问

DLX 能保证绝不丢吗？——不能简单保证。需要结合 Queue 类型、dead-letter strategy、目标 Queue 可用性以及幂等补偿设计。

② 新题 2｜哪些情况会成为死信？

原资料：《后端高频面试题大集合》MQ 第15题｜PDF 第92～93页。正式后端 #66。

概念与原理

原资料列出 reject/nack 且不 requeue、TTL 过期、Queue 长度/存储限制等情况。现代 RabbitMQ 还需要注意 Quorum Queue 的 delivery-limit。

触发含义
basic.reject / basic.nack + requeue=falseConsumer 明确拒绝继续重投
TTL expired消息达到过期条件
Queue length limit超过 Queue 限制时按策略处理
Quorum delivery-limit消息重复投递超过限制

为什么

Poison Message 如果无限 requeue，会形成高频失败循环，浪费 CPU/网络并阻塞正常消息，因此需要重试上限和隔离。

实际项目怎么用

业务异常先判断 transient / permanent：临时网络异常可有限重试；参数非法、数据状态不允许等永久失败应尽快进入 DLQ，保留 messageId、traceId、errorCode 供补偿。

AI补充/纠错：原资料把“unroutable message”直接列为 Queue 死信原因不严谨。消息如果在 Exchange 路由阶段根本没有进入 Queue，通常属于 unroutable publishing，应使用 mandatory/return 等机制处理，而不是把它和 Queue 内 dead-lettering 混为一谈。

常见坑

所有异常都 requeue=true；没有最大重试次数；DLQ 没有告警；人工重放时没有幂等。

面试口述版：典型死信包括消费端 reject/nack 且不 requeue、消息 TTL 过期、Queue 超过长度限制，以及 Quorum Queue 超过 delivery-limit。工程上重点是防止 poison message 无限重试，并给 DLQ 配监控和补偿。

可能追问

为什么 TTL 到了不一定立刻从队列统计中消失？——过期消息的实际清理与其在队列中的位置和队列实现有关，不能把 TTL 当精确调度器。

② 新题 3｜Kafka KRaft 架构相比 ZooKeeper 改进了什么？

原资料：《后端高频面试题大集合》MQ 第16题｜PDF 第93～94页。正式后端 #67。

概念

KRaft（Kafka Raft）把 Kafka 集群元数据管理从外部 ZooKeeper 迁移到 Kafka 自身的 Controller Quorum，由 Controller 通过 Raft 风格的元数据日志管理集群状态。

原理 → 为什么

旧架构：Broker ↔ ZooKeeper + Controller
KRaft：Broker ↔ Controller Quorum ↔ Metadata Log

减少一套外部协调系统后，部署、运维和元数据一致性模型更统一，也为更大规模集群和更快 Controller 切换提供基础。

实际项目怎么用

新 Kafka 集群直接按 KRaft 规划 Controller/Broker 角色、Controller Quorum、存储和监控，不再把 ZooKeeper 当 Kafka 必选组件。

AI补充/纠错：原资料说 KRaft 是“Kafka 2.8 引入的新架构”适合作为历史背景，但面试应补充当前状态：KRaft 已从“可选新模式”发展为现代 Kafka 的标准方向。不要把 KRaft 简化成“把 ZooKeeper 换成几个 Controller”，核心变化是 Kafka 自己维护复制的元数据日志与 Controller Quorum。

常见坑

把业务 Topic 数据复制和元数据 Quorum 混为一谈；Controller 数量随意设置；只关注迁移步骤却不知道 KRaft 解决的架构问题。

面试口述版：KRaft 的核心是让 Kafka 自己通过 Controller Quorum 管理复制的元数据日志，去掉 ZooKeeper 依赖，从而简化部署运维，并统一 Kafka 的元数据一致性和故障切换机制。

可能追问

Controller Quorum 和 Topic Partition Replica 是一回事吗？——不是。前者主要维护集群元数据共识，后者承载业务消息数据。

② 新题 4｜Function Call：模型生成 JSON 后怎样触发 Java 代码？

原资料：《AI应用开发面试题 / Agent / RAG》Tool Calling / Function Call / MCP 专题 1.1.2｜PDF 第39页起。原 PDF 在 1.1.22 后进入新的 Tool Calling 专题并重新编号，按原资料保留。

概念

Tool Calling 不是模型自己执行 Java 方法。模型根据 Tool Schema 和用户意图输出结构化 tool_call，应用层解析后找到允许的函数，校验参数并执行，再把 tool_result 回传给模型。

原理 → 为什么

User Query
   ↓
LLM + Tool Schema
   ↓
tool_call{name,args}
   ↓
Java Tool Registry / Callback
   ↓
参数校验 + 权限 + 真实 Service/API
   ↓
tool_result
   ↓
LLM → Final Answer

模型知道“调用哪个工具”主要依赖训练阶段学到的 Tool Calling 模式，以及推理时对用户意图、tool description、parameter schema 的语义匹配。

实际项目怎么用

Spring AI 中可以把查询订单、读取数据库、发送 Push 等能力暴露为受控 Tool；Java Service 仍然负责事务、安全、超时和异常处理。

AI补充/纠错：不要把 Tool Schema 理解成普通 System Prompt 文本。不同模型提供商通常通过专门的 tools/tool definitions 协议字段传递。Schema 能限制结构，但不能替代业务授权。对于删除、支付、发送消息等副作用操作，还应加入确认、幂等键和审计。

常见坑

模型输出什么函数名都反射执行；参数只做 JSON 反序列化不做业务校验；Tool Result 太大直接塞回上下文；重试导致副作用重复执行。

面试口述版：模型并不会直接执行代码，它根据 Tool Schema 输出 tool_call；Agent 框架或 Java 应用把 tool name 映射到白名单 Callback，校验参数和权限后执行真实 Service，再把结果回传模型继续推理。

可能追问

为什么 Tool Calling 比让模型输出一段 Java 代码再执行安全？——因为可执行能力被限制在预注册白名单工具中，参数和权限可以在应用层强制校验。

② 新题 5｜什么是 RAG？核心流程是什么？

原资料：《AI大模型面试题-基础篇》RAG 第27题｜PDF 第22～23页。原 PDF 在“幻觉问题”后跳转到第27题，编号按原资料保留。

概念

RAG（Retrieval-Augmented Generation）是在生成前先从外部知识源检索与问题相关的证据，再把问题与证据一起交给 LLM 生成答案。

原理 → 为什么

离线：Document → Chunk → Embedding → VectorStore

在线：Question → Query/Embedding → Retrieve Top-K
                           ↓
                    Relevant Chunks
                           ↓
Question + Evidence → LLM → Answer + Citation

它把“知识更新”从重新训练模型转为更新外部知识库，适合企业文档、政策、产品手册等经常变化且需要可追溯来源的场景。

实际项目怎么用

Spring AI 项目可使用 Document/Reader/Splitter、EmbeddingModel、VectorStore 与 RAG Advisor 组织检索链路。企业知识库还要把 userId、companyId、departmentId、fileId、permission 等放入 metadata，在检索阶段做 ACL Filter。

AI补充/纠错：RAG 不等于“向量库 + TopK”。生产质量还取决于文档解析、Chunk、Metadata、Query Rewrite、Hybrid Search、Rerank、ACL、Context Assembly 和 Eval。RAG 只能降低幻觉概率，不能保证答案一定正确。

常见坑

Chunk 过大/过小；只做向量相似度不做权限过滤；Top-K 越大越好；知识更新后旧向量未删除；没有引用和离线 Eval。

面试口述版：RAG 是先检索外部知识，再把检索证据和用户问题一起交给模型生成。它能提高知识时效性和可追溯性、降低频繁微调成本。Spring AI 中我会用 VectorStore + RAG Advisor 实现，并在企业场景加入 metadata ACL、Rerank 和 Eval。

可能追问

RAG 与 Fine-tuning 怎么选？——经常变化、需要引用的事实知识优先 RAG；希望改变模型行为、风格或特定能力时再考虑微调，两者也可以组合。
